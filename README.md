# Harness

Harness is a local-first control plane for coding agents. It preserves project intelligence across agent sessions and hosts while keeping source editing, shell access, Git, and browsing in the native host.

> **Repository status:** implementation foundation. The supported POSIX/Linux local path now includes Claude Code, Codex local CLI/IDE/desktop project MCP, and Cursor IDE/CLI adapters, ownership-aware lifecycle orchestration, exact Workspace-root resolution, duplicate-free shared skill projection, operational doctor checks, installed-wheel cross-interpreter continuity, and upgrade-safe daemon replacement. Proprietary-host Codex/Cursor acceptance, Antigravity MCP, richer structural/symbol retrieval, Working Sets, and optional embeddings remain open. Durable Project/Workspace, Task/Knowledge, deterministic index, dashboard, and the official five-tool MCP bridge remain host-neutral core state.


## Product principles

- One global Harness installation, isolated project context.
- Native-agent-first integration through MCP.
- Progressive disclosure instead of bulk context dumps.
- Filesystem and Git remain sources of truth for code and repository state.
- Semantic knowledge is captured only after real task investigation and always has provenance.
- A small, stable model-facing surface: status, search, context, task start/resume, checkpoint.
- One modular-monolith core; host-specific behavior stays in adapters.
- Two explicit publication modes: Normal for ordinary native-host SCM behavior, Hidden for local-only agent integration with human-owned Git/SCM publication. Operators enable Hidden from the dashboard or with `harness visibility hidden`; Harness projects untracked host rules and Git-local excludes. Cursor still does not host-block git/PR.

## Linux local use with Cursor or Codex

The primary Linux local close-out is Cursor IDE/CLI in Normal mode: `harness install --host cursor`. Claude Code and Codex are also implemented. Omitting `--host` still selects `claude-code` for compatibility; install each compatible active profile explicitly.

`uv tool install` of this repository requires `uv` 0.12.5. Checkout development uses the same version via `scripts/dev` (bootstrapped into `.harness/tools/uv` when needed). System `uv` 0.12.1 cannot install this repo.

```bash
uv tool install --python 3.13 .
harness install --host cursor
harness doctor
harness backup /safe/path/harness-$(date +%F).harness-backup
cd /path/to/git/repository
harness scan
harness visibility hidden   # operator-only; projects local rules + git info/exclude
# After Harness changes Cursor MCP config, fully quit and reopen Cursor.
agent mcp list
harness status
```

Durable recovery uses `harness backup ARCHIVE` and `harness restore ARCHIVE`. Backup is safe while
the daemon is running and captures committed WAL content. Restore validates the archive checksum,
SQLite integrity, exact schema, and creating runtime identity, cleanly stops the daemon, and keeps a
timestamped pre-restore backup beside the database. A reviewed exact-schema archive from another
Harness build requires the explicit `--allow-runtime-mismatch` flag. Backup archives can contain
Task and Knowledge text and should be protected like the database itself. See
[ADR-0036](docs/decisions/0036-durable-state-backup-and-restore.md).

Claude Code remains `harness install` / `harness install --host claude-code`. Install a compatible Claude+Cursor pair by running the two profile commands sequentially; `--host all` is intentionally rejected because adding Codex would create the unsupported three-host skill graph. Current Claude Code `claude mcp get` absent-server text (quoted or unquoted) is classified as absent, so Claude CLI output drift is not a Cursor doctor/install/uninstall/scan blocker. Unexpected Claude inspect failures still fail doctor; true absence remains a warning.

Codex local setup is `harness install --host codex`, followed by `harness scan` in each Git
Workspace and a Codex restart. Harness creates only an ignored, marker-owned project
`.codex/config.toml`; it does not mutate `~/.codex/config.toml` or project trust. Run
`codex mcp get harness --json` from a trusted Workspace root to verify discovery. Codex and Cursor
share `.agents/skills`; Codex and Claude use their respective native roots. Installing all three is
refused before mutation because Cursor would see duplicate skills from the Claude and Codex roots.
In Hidden projects the same owned project config adds exact `developer_instructions`; Codex loads
that trusted project layer without replacing user-owned `AGENTS.md`. This is hygiene-effective
Hidden, not a claim that Codex host-blocks Git/PR publication.

Cursor's current official docs require a restart after editing `mcp.json`; Harness prints that restart/reopen reminder whenever install, scan, or uninstall actually changes Cursor MCP configuration. When the official Cursor `agent` CLI is installed, `harness install --host cursor` and `harness scan` run `agent mcp enable harness` from each Workspace and verify `agent mcp list-tools harness`. Missing `agent` prints `cd <workspace> && agent mcp enable harness` plus a full Cursor quit/reopen. Leftover `user-harness` is not Workspace identity and is removed. Isolated Harness source checkout uses `harness-dev`. These probes are not proprietary Cursor UI/CLI acceptance; that matrix in [`docs/host-compatibility.md`](docs/host-compatibility.md) remains unchecked.

Claude Code registration remains owned through the official `claude mcp` CLI and resolves the active Workspace from `CLAUDE_PROJECT_DIR`. Codex and Cursor production MCP are project-only and use Harness-owned intent rather than global-config presence. Codex binds an absolute root in `.codex/config.toml`; Cursor uses `.cursor/mcp.json` with `HARNESS_WORKSPACE_ROOT=${workspaceFolder}`. Neither bridge treats process cwd or self-reported client metadata as profile Workspace identity. A profile process without its required explicit root lists no tools. `harness scan` reconciles one compatible active-profile set and fails closed when the visibility graph would duplicate skills.

`harness uninstall --host claude-code|codex|cursor|all` removes only selected Harness-owned host artifacts while preserving Project Intelligence and any other active host. The daemon remains alive while another supported host is active; `--purge` is refused in that state. Tracked Cursor/Codex project config is manual-adoption/manual-removal only, so Harness never creates a dirty tracked diff. `harness dashboard` and `harness skills list` remain host-neutral. See [`docs/release-linux.md`](docs/release-linux.md), [ADR-0024](docs/decisions/0024-linux-cursor-multi-host-lifecycle.md), [ADR-0026](docs/decisions/0026-cursor-project-scoped-workspace-mcp.md), and [ADR-0030](docs/decisions/0030-codex-project-scoped-workspace-mcp.md). Codex cloud and Cursor Cloud Agents are separate profiles.

## Development state

The repository now has a Python 3.13 package, a locked development toolchain, and SQLite schema version 14. Database initialization creates ordered migration metadata, requires WAL mode, enables foreign-key enforcement for Harness connections, probes the required FTS5/contentless-delete capabilities at runtime, and migrates the bootstrap schemas forward without discarding unrelated existing data.

Schema v14 contains the durable Project/Workspace registry, the rebuildable `indexed_files` Structural Index slice, bounded contentless FTS5 code/docs retrieval, durable Task/CAS state, one-to-one mechanical Task baseline storage, immutable Task checkpoint/event history, bounded operator feedback/comments, Jira and delivery-marker state, and rebuildable FTS5 candidate indexes for Knowledge and Task semantic retrieval. Task rows remain Workspace-owned, use the minimal `working`/`waiting`/`completed`/`cancelled` lifecycle states, require an allowed reason only while waiting, and carry a positive monotonic revision. A partial unique SQLite index enforces at most one distinct `working` Task per Workspace even if a caller bypasses normal domain checks. Existing-Task mutations require explicit `task_id` plus `expected_revision`; successful mutations increment revision exactly once and stale revisions are non-mutating. Human review uses the same contract: Accept completes only a Task waiting for `operator_review`, feedback atomically persists bounded operator text and resumes that same Task, comments/Jira/delivery markers remain lifecycle-independent, explicit reopen returns one terminal Task to `working`, and cancel terminates an explicit non-terminal Task. Pending feedback is surfaced through `project_status` only while it is attached to the current working revision, then clears after the next checkpoint.

The baseline-aware internal creation path now atomically captures the required mechanical start state before committing a new Task at revision 1. A baseline records Git HEAD/branch, UTC timestamp, current persisted Structural Index count/digest, a direct read-only `index_is_fresh` comparison against a live deterministic inventory, and every pre-existing Git dirty path with porcelain status, rename/copy origin when present, and a SHA-256 state fingerprint. Regular-file fingerprints include local file bytes but persist only the digest; symlinks hash the target string without following it for content; missing paths use a sentinel. Dirty submodules/directories and other entries that Harness cannot completely fingerprint are explicitly marked `opaque` so later comparisons remain conservative instead of producing false confidence. Baseline capture samples Git state twice around live-index inspection, verifies Workspace/Git identity, has a finite deadline, and rolls back Task creation if capture fails.

The internal changed-file calculator now compares that durable baseline with a stable current Git/worktree sample without mutating Task state or consulting the Structural Index. Exact unchanged non-opaque pre-existing dirty records are excluded; new dirtiness, changed/cleaned pre-existing dirtiness, conservative opaque entries, and committed tree deltas since the baseline HEAD are included. Task-time rename/copy records contribute both destination and origin paths. The calculation shares a finite deadline across baseline-row streaming, Git identity, dirty-content fingerprinting, committed-tree comparison, and deterministic result merging, and it fails closed if Workspace/Git state changes during the read.

The checkpoint persistence layer applies a checkpoint only to the explicitly named `working` Task using `task_id` plus `expected_revision`. A successful checkpoint increments Task revision exactly once and atomically stores bounded summary/next-step semantics, checkpoint state/wait reason, cumulative mechanical changed paths since Task start, current Git HEAD/branch/dirty-path count, provenance-bearing Knowledge, and an immutable checkpoint timeline event. Stale writers and mechanical calculation failures are fully non-mutating. Public `task_start`/resume and `task_checkpoint` are exposed through bounded daemon IPC and the MCP bridge. Checkpoints now persist bounded agent-reported verification records (`name`, `passed|failed|not_run`, `evidence`) atomically with Task state and expose compact status through `project_status` plus bounded evidence through selected Task context; bridge activity history remains a later slice.

New Projects are created with the required `normal` visibility default. The low-level explicit registration primitive remains internal and requires an explicit Project identity plus an inspectable Git worktree; Harness stores the canonical worktree root and Git common directory reported by Git, treats repeat registration as idempotent, fails closed on incompatible root/Project identity, and rejects contradictory visibility policy for Workspaces sharing one Git common directory. Public scan registration reuses an already registered root, attaches a new linked worktree to the one unambiguous existing Project sharing its Git common directory, and creates a new Project for a Git checkout whose common directory is not registered. It does not infer logical Project identity across independent clones or expose visibility-mode transitions.

The deterministic index inventories regular files and symlinks for one registered Workspace, stores relative path, entry kind, byte size, and SHA-256 mechanical identity, and reconciles additions/changes/deletions transactionally. Candidate enumeration uses Git tracked/untracked state with standard Git ignores, `.harnessignore`, common generated-directory exclusions, and default sensitive patterns such as `.env`, PEM, and key files. Symlink targets are hashed as link metadata rather than followed for source content, and symlinked parent paths that escape the Workspace fail closed. Regular UTF-8 files up to 1 MiB also feed a contentless code/docs FTS projection after a second stable read matches the mechanical hash; source bodies are not readable back from SQLite. Binary/NUL, invalid-UTF-8, symlink, oversized content, and generated `.log`/`.out` diagnostic text remains available only to the mechanical inventory/path boundary. Daemon-backed scans carry a finite execution deadline and update the path index, lexical projection, and Knowledge staleness in one transaction. The POSIX daemon's bounded watcher treats Git/filesystem observations only as invalidation hints, debounces changes, and serializes with explicit scans. Idle polls use a subprocess-free metadata token; changed bounded same-HEAD dirty paths use canonical incremental index/FTS/Knowledge reconciliation. Existing/restarted Workspaces, HEAD/policy/large changes, and the slower periodic safety pass still receive a full authoritative reconciliation. The index and FTS projection remain derived/rebuildable data; parser-backed symbols and structural graphs are still later slices.

The mechanical CLI search remains deterministic Workspace-scoped path retrieval over current `indexed_files` rows. MCP `project_search` additionally searches bounded local UTF-8 code/docs content through the contentless FTS5 projection, so natural queries no longer require every word to occur in a filename. Query analysis handles Unicode, common camel/snake identifiers, conversational filler, prefixes, and conservative English/Russian inflections. Ranking uses explainable tiers—exact path, exact filename, exact filename stem, title/identifier phrase, all significant terms, then partial match—and deterministically fuses code, docs, fresh/stale Knowledge, and Task history without exposing internal scores. Generated diagnostic output is excluded from scoped code/docs results; test and archive paths receive same-tier penalties unless requested explicitly. Directly matching fresh Knowledge can lead general lexical hits; `needs_revalidation` cards remain explicit historical clues and follow fresh cards. Every code/doc result and selected context ref is reconstructed from current authoritative `indexed_files`; result/context payloads remain metadata-only and raw source remains a native-host read. Symbols/structural graph search, Working Sets, translation, and optional embeddings remain later slices.

The installed `harness` CLI includes the complete supported Linux `harness doctor` boundary. Bare `doctor` is read-only and inspects SQLite/FTS5, canonical permissions/artifacts, Claude adapter and MCP ownership, the daemon's frozen runtime identity, database/schema state, registered Project/Workspace Git identity, deterministic index freshness, canonical/generated skills, dashboard subsystem state, and stale integrations under bounded live-Workspace deadlines. Index and generated-skill warnings distinguish inspection timeouts and doctor-budget truncation from Project `unavailable` Git/identity failures, and they name the affected Workspace. Warnings do not make the command fail; integrity/ownership/compatibility failures do. It never starts the daemon/dashboard, scans, registers, or reconciles state. `harness doctor --runtime-only` preserves the original ephemeral in-memory SQLite/FTS5 probe, while `harness doctor --database PATH` performs read-only inspection of one explicitly selected initialized database.

The supported Linux/POSIX installation lifecycle is exposed as `harness install|uninstall --host claude-code|codex|cursor|all`. The primary local close-out is `harness install --host cursor`; omitted `--host` still preserves the previous Claude Code default. Install verifies SQLite/FTS5, host ownership, compatible skill visibility, Hidden admission, and the frozen daemon identity before mutation. `--host all` is a valid uninstall selection but install rejects the incompatible three-host skill graph. Partial uninstall reconciles skills against the remaining profiles and keeps the daemon alive; uninstall of the last active host performs owned skill cleanup and clean shutdown. Project Intelligence is preserved unless `--purge` is explicitly requested, and purge is refused while another supported host remains active. Cursor and Codex project-config refresh skip registered Workspace roots that cannot be resolved as directories, name them as skipped unavailable Workspaces, and continue with live checkouts; `harness doctor` still WARNs those registry rows. Harness-owned Codex project MCP is marked required and forwards only configured non-empty bounded environment selectors, so MCP initialization fails visibly without producing missing-variable diagnostics for unset optional selectors.

The installed CLI exposes `harness scan [PATH] [--socket PATH]`. It resolves and durably registers the canonical Git worktree, performs deterministic local indexing, reconciles active Codex/Cursor project MCP configs, and submits the complete compatible profile set to one daemon-owned skill reconciliation. Absent intent never authorizes project config mutation. If later host/skill reconciliation fails, the registered Workspace remains and retry reuses it. Canonical daemon autostart is bounded; explicit `--socket` never autostarts it.

The installed CLI also exposes `harness status [PATH] [--socket PATH]`. `PATH` defaults to the current directory and is treated as a filesystem location inside an already registered Workspace. The command resolves that location through the daemon's fail-closed Workspace resolver and prints only compact mechanical state: Project/Workspace identity, canonical root, visibility mode, Git branch/HEAD, dirty-path summary, indexed-file count, and schema version. It is read-only: it does not register a Project/Workspace, run a scan, or mutate the database. With no `--socket`, it validates/reuses the canonical per-user daemon and lazily starts it when the local transport is unavailable. A missing runtime directory is allowed only as a first-run state; once it exists, the client requires a real current-user-only directory before trusting the socket. Explicit `--socket` usage remains caller-managed and does not autostart the canonical daemon.

The installed CLI now also exposes `harness dashboard [--socket PATH]`. The daemon starts its loopback Projects dashboard as soon as it is serving: one HTTP server bound to `127.0.0.1:17373` for the canonical per-user daemon, or `127.0.0.1:17374` when `HARNESS_DEV_ROOT` isolates a checkout. Explicit `--socket` overrides keep an ephemeral port. The command prints the private capability-bearing URL; it does not start a second listener. The current URL is also written to `dashboard.url` (mode `0600`) in the same private runtime directory as the Unix socket and is removed when the dashboard stops. The capability path token is persisted next to the selected database as `dashboard.token` (mode `0600`) so the full URL stays stable across daemon restarts. The server is owned by the daemon lifetime, disables access logging, and exposes no unscoped root page: the URL path is returned only through local IPC or that runtime file. The operator UI is Russian and limited to current work: Projects, Workspaces, current Task state, Jira navigation, delivery marker, review actions, comments, bounded Task/path search, and the Task timeline. MCP server instructions and the `task_start`/`task_checkpoint` descriptions tell agents to write Task titles, summaries, next steps, and Knowledge cards in Russian; the dashboard renders that stored text rather than translating it. It does not explain the product, loopback trust model, or Harness architecture. The Projects overview links into capability-scoped Project, Workspace, and Task detail pages. Project detail can permanently remove an obsolete Project and all of its Harness history after typed confirmation without deleting repository files. Workspace detail can rebind a moved checkout to a new absolute Git path while preserving Project, Workspace, Task, and Knowledge identity; it clears the rebuildable index until the watcher scans the new root and tells the operator to run `harness scan` there to refresh adapter-owned project settings. Workspace detail also combines deterministic bounded indexed-path results with Project-scoped Task hits over titles, checkpoints, branches, Jira, feedback, comments, and delivery markers; Task detail renders bounded durable history plus operator controls without raw source. Accept, feedback, comments, Jira/status changes, explicit reopen, cancel, and Hidden/Normal still post through the exact same revision-CAS domain workflow and require exact loopback Host plus same-origin Origin or `Sec-Fetch-Site: same-origin` when Origin is absent, and the rendered Task revision. Project deletion and Workspace relocation additionally require the posted identity to match the detail page. Capability-scoped CSS/JavaScript assets allow a strict same-origin CSP without inline script/style. SSE is a bounded presentation-only freshness hint: an initial authoritative view fingerprint closes the render/connect race, then a persistent read-only SQLite connection watches `data_version` and emits only `ready`/`refresh`, never Task/source payloads; the browser delays reload when it would destroy unsaved feedback/search input. Persisted Task/operator text is HTML-escaped, all responses remain `no-store`/`nosniff`/`no-referrer` without `Server`/`Date`, and missing/replaced Git Workspaces retain durable state while live status fails closed.

On supported POSIX systems the canonical daemon database is `$XDG_STATE_HOME/harness/harness.db` when `XDG_STATE_HOME` is an absolute path, otherwise `~/.local/state/harness/harness.db`. The canonical socket is `$XDG_RUNTIME_DIR/harness/harness.sock` when `XDG_RUNTIME_DIR` is absolute, otherwise `<system temporary directory>/harness-<effective uid>/harness.sock`. Empty/relative XDG values are ignored. Before the default database is used, the final Harness state directory is created/validated as a real (non-symlink) current-user-only directory. The daemon similarly requires its final socket directory to be a real current-user-only directory before bind, so pre-created symlink entries in a shared temporary namespace fail closed.

The installed `harnessd` console script exposes `harnessd serve [--database PATH] [--socket PATH]`. With no overrides it initializes/migrates the canonical per-user database and binds the canonical per-user Unix-domain socket. The daemon serves global/Workspace status, compact Task-continuity status, bounded Workspace search, deterministic Workspace scan, Task start/resume/checkpoint requests, and the loopback Projects dashboard with its revision-CAS human review actions. The dashboard listener starts with the daemon rather than on first `harness dashboard` request. Task writes remain explicit-identity/CAS operations; the MCP bridge never writes SQLite directly. The two path options remain available independently for development, tests, recovery, or isolated manual operation; concurrent isolated daemon instances require distinct selected Harness databases. On supported POSIX systems the socket directory must be a real directory owned by the current OS user with no group/other access. Harness holds process-lifetime `flock` ownership for both the selected socket endpoint (`<socket>.lock`) and the resolved selected database (`<database>.lock`), with both lock files secured to `0600`. The endpoint lock is acquired before stale-socket classification; the database lock is acquired before SQLite initialization/migration. A competing daemon therefore cannot reuse the endpoint or become a second writer for the same Harness database through another socket or an equivalent database path alias. If the endpoint lock is free after a crash, Harness removes an existing same-user Unix socket only when it cannot accept a connection and its device/inode identity is unchanged at unlink time; connectable sockets and non-socket/unsafe entries fail closed. Harness creates a missing final runtime directory with mode `0700`, sets the served socket to `0600`, removes only the socket inode it created on clean shutdown, and intentionally leaves the reusable lock files in place. These singleton rules also make concurrent lazy-autostart attempts safe: racing clients may launch more than one process, but only one can acquire the canonical endpoint/database ownership.

The global status result remains deliberately small: schema version plus Project and Workspace counts. `workspace_status` accepts at most four ordered absolute filesystem hints, resolves them against the durable Workspace registry with the existing fail-closed priority rules, verifies the registered Git identity, and returns only compact mechanical state: Project/Workspace identity, effective visibility mode, canonical Workspace root, live Git branch/HEAD, dirty-path count, and current indexed-file count. It does not expose source text, search results, Tasks, Knowledge, or MCP objects. `workspace_search` uses the same bounded hint contract, additionally accepts the bounded query and item limit, verifies registered Git identity around a consistent database read snapshot, and returns only Project/Workspace identity plus mechanical search hits. It never returns indexed content hashes or source content.

The current internal IPC protocol is independent of MCP wire objects, uses protocol version `1`, allows exactly one request/response per connection, enforces a 16 KiB message limit, uses bounded request/response timeouts, and rejects unknown fields/methods fail-closed. `dashboard_url`, `shutdown`, `runtime_diagnostics`, `workspace_status`, `workspace_task_status`, `workspace_search`, `workspace_index_entry`, `workspace_skills_reconcile`, `skill_cleanup`, `project_search`, `project_context`, `scan_workspace`, `task_start`, and `task_checkpoint` are additive protocol-v1 methods; the original global `status` wire shape remains unchanged. The release upgrader deliberately supports the immediately preceding protocol-v1 daemon that does not know `runtime_diagnostics`: only its structured `invalid_request` response activates a compatibility path that validates legacy `status`, requests the already-supported clean `shutdown`, and then verifies a newly started current-runtime daemon. Other diagnostics failures remain fail-closed. The scan and Task clients use longer bounded receive timeouts for their bounded mechanical work. Canonical POSIX clients lazily start the daemon from the installed Python package when needed, with a three-second readiness bound and existing runtime-directory validation. Windows daemon IPC and canonical Windows transport paths remain unsupported until that separate platform task is proven.

The first skills slice loads a canonical external registry from `~/.harness/skills`, keeps Harness applicability metadata in `harness.yaml` separate from portable `SKILL.md`, derives deterministic stack evidence, and combines it with durable Task hints under a bounded visible-skill budget. Contextual facets distinguish ambiguous roles—for example Expo/React Native from React Web—without losing multi-surface monorepo coverage. Once any skill recognizes the current Task hints, they focus projection on task-matched skills plus explicit inclusions instead of filling the remaining budget from unrelated polyglot surfaces; unknown hints safely retain the stack baseline. Built-in descriptions state their activation boundary for host-native discovery. Harness seeds a compact stack-aware quality pack and reconciles only Harness-owned exact content, including nested progressive-disclosure references. The pack covers container and deployment operations, public frontend SEO/performance, mobile apps, backend services, Godot, project and legacy architecture, language-native engineering, data integrity, secure-by-design architecture/verification, testing, observability, delivery, and review; no more than the configured relevant subset is projected. Projection planning models host compatibility roots so every active profile sees exactly one Harness copy or the operation fails closed. `harness scan` supplies the union of current Claude Code, Codex, and Cursor profiles to that planner: Codex+Cursor reuse `.agents/skills`, Claude+Codex use native roots, and the three-host graph fails before mutation because Cursor would see both. Partial uninstall recomputes remaining projections; final uninstall removes only Harness-owned generated skills. Automated fixtures prove these mechanics; proprietary-host visibility remains acceptance-gated.

The installed CLI also exposes `harness mcp`, implemented with the official `mcp==2.0.0` SDK and the MCP 2026-07-28 sessionless protocol path. The stdio boundary rejects oversized or concurrently duplicated JSON-RPC request identities before dispatch and bounds every serialized outbound frame, so untrusted envelope fields cannot bypass model-facing byte budgets or trigger a Task mutation whose response cannot be correlated safely. Request-ID collision checks use the official SDK correlation semantics, so integer IDs and their stringified forms share one in-flight identity.
