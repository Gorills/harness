# Harness

Harness is a local-first control plane for coding agents. It preserves project intelligence across agent sessions and hosts while keeping source editing, shell access, Git, and browsing in the native host.

> **Repository status:** implementation foundation. Packaging/tooling, SQLite persistence, Project/Workspace registry primitives, read-only runtime doctor checks, Workspace status, deterministic scan, bounded indexed-path search, POSIX daemon lifecycle/autostart, durable Task/CAS with mechanical baselines/checkpoints, provenance-bearing Knowledge staleness, daemon Task IPC, the first daemon-owned incremental Workspace watcher, and the official MCP v2 stdio bridge exist. Adapters for hosts other than Claude Code, real-host acceptance, richer search/context channels, dashboard actions/SSE, and final install/uninstall orchestration are not implemented yet. A first read-only daemon-owned Projects dashboard now exists. Deterministic skill registry loading/resolution and collision-safe project projection mechanics now exist, including Task stack hints and Git-local generated-skill exclusion; real-host skill visibility remains acceptance-gated. The first Claude Code adapter now owns user-scope MCP registration mechanics and documented project-root hint construction, but it is not yet wired into the final multi-host `harness install`/`uninstall` orchestration.

## Product principles

- One global Harness installation, isolated project context.
- Native-agent-first integration through MCP.
- Progressive disclosure instead of bulk context dumps.
- Filesystem and Git remain sources of truth for code and repository state.
- Semantic knowledge is captured only after real task investigation and always has provenance.
- A small, stable model-facing surface: status, search, context, task start/resume, checkpoint.
- One modular-monolith core; host-specific behavior stays in adapters.
- Two explicit publication modes: Normal for ordinary native-host SCM behavior, Hidden for local-only agent integration with human-owned Git/SCM publication.

## Development state

The repository now has a Python 3.13 package, a locked development toolchain, and SQLite schema version 9. Database initialization creates ordered migration metadata, requires WAL mode, enables foreign-key enforcement for Harness connections, probes FTS5 as a runtime capability, and migrates the bootstrap schemas forward without discarding unrelated existing data.

Schema v9 contains the durable Project/Workspace registry, the rebuildable `indexed_files` Structural Index slice, durable Task/CAS state, one-to-one mechanical Task baseline storage, and immutable Task checkpoint/event history. Task rows remain Workspace-owned, use the minimal `working`/`waiting`/`completed`/`cancelled` states, require an allowed reason only while waiting, and carry a positive monotonic revision. A partial unique SQLite index enforces at most one distinct `working` Task per Workspace even if a caller bypasses normal domain checks. Existing-Task state transitions still require explicit `task_id` plus `expected_revision`; successful transitions increment revision exactly once, stale revisions are non-mutating, and completed/cancelled Tasks are terminal.

The baseline-aware internal creation path now atomically captures the required mechanical start state before committing a new Task at revision 1. A baseline records Git HEAD/branch, UTC timestamp, current persisted Structural Index count/digest, a direct read-only `index_is_fresh` comparison against a live deterministic inventory, and every pre-existing Git dirty path with porcelain status, rename/copy origin when present, and a SHA-256 state fingerprint. Regular-file fingerprints include local file bytes but persist only the digest; symlinks hash the target string without following it for content; missing paths use a sentinel. Dirty submodules/directories and other entries that Harness cannot completely fingerprint are explicitly marked `opaque` so later comparisons remain conservative instead of producing false confidence. Baseline capture samples Git state twice around live-index inspection, verifies Workspace/Git identity, has a finite deadline, and rolls back Task creation if capture fails.

The internal changed-file calculator now compares that durable baseline with a stable current Git/worktree sample without mutating Task state or consulting the Structural Index. Exact unchanged non-opaque pre-existing dirty records are excluded; new dirtiness, changed/cleaned pre-existing dirtiness, conservative opaque entries, and committed tree deltas since the baseline HEAD are included. Task-time rename/copy records contribute both destination and origin paths. The calculation shares a finite deadline across baseline-row streaming, Git identity, dirty-content fingerprinting, committed-tree comparison, and deterministic result merging, and it fails closed if Workspace/Git state changes during the read.

The checkpoint persistence layer applies a checkpoint only to the explicitly named `working` Task using `task_id` plus `expected_revision`. A successful checkpoint increments Task revision exactly once and atomically stores bounded summary/next-step semantics, checkpoint state/wait reason, cumulative mechanical changed paths since Task start, current Git HEAD/branch/dirty-path count, provenance-bearing Knowledge, and an immutable checkpoint timeline event. Stale writers and mechanical calculation failures are fully non-mutating. Public `task_start`/resume and `task_checkpoint` are exposed through bounded daemon IPC and the MCP bridge; verification records, dashboard mutations, and bridge activity history remain later slices.

New Projects are created with the required `normal` visibility default. The low-level explicit registration primitive remains internal and requires an explicit Project identity plus an inspectable Git worktree; Harness stores the canonical worktree root and Git common directory reported by Git, treats repeat registration as idempotent, fails closed on incompatible root/Project identity, and rejects contradictory visibility policy for Workspaces sharing one Git common directory. Public scan registration reuses an already registered root, attaches a new linked worktree to the one unambiguous existing Project sharing its Git common directory, and creates a new Project for a Git checkout whose common directory is not registered. It does not infer logical Project identity across independent clones or expose visibility-mode transitions.

The first deterministic index slice inventories regular files and symlinks for one registered Workspace, stores only relative path, entry kind, byte size, and SHA-256 mechanical identity, and reconciles additions/changes/deletions transactionally. Candidate enumeration uses Git tracked/untracked state with standard Git ignores, `.harnessignore`, common generated-directory exclusions, and default sensitive patterns such as `.env`, PEM, and key files. Symlink targets are hashed as link metadata rather than followed for source content, and symlinked parent paths that escape the Workspace fail closed. The index is derived/rebuildable data. Daemon-backed scans carry a finite execution deadline; deadline expiry rolls back an in-progress index reconciliation. The POSIX daemon now runs a bounded background watcher that treats Git/filesystem observations only as invalidation hints, debounces changes, serializes with explicit scans, and always reconciles through the same deterministic `scan_workspace` path. Existing Workspaces receive an initial reconciliation after daemon restart, and a slower periodic full reconciliation repairs missed hints. The watcher does not add another source of truth or persist/return source contents; content hashing remains part of the authoritative reconciliation scan. This slice still does not parse symbols/languages or populate FTS.

The first search slice performs deterministic, Workspace-scoped retrieval over current `indexed_files` rows without reading or returning source text. It ranks exact relative-path matches, exact filenames, normalized ASCII identifier-token matches (including common camel/snake/kebab/dotted forms), then case-insensitive path substrings. Queries are bounded to 256 UTF-8 bytes, result count is hard-bounded to 50 with a default of 10, and each hit exposes only relative path, entry kind, size, and the mechanical match reason. The installed CLI exposes this as `harness search QUERY [PATH] [--limit N] [--socket PATH]`; MCP `project_search` exposes the same mechanical channel with a smaller model-facing default/hard limit and returns stable `code:` references for selective `project_context` expansion. FTS/content search, symbols, semantic Knowledge/Task retrieval, Working Sets, and rank fusion remain later slices.

The installed `harness` CLI includes `harness doctor`. With no database argument it checks the current SQLite runtime and FTS5 availability using only an in-memory database, so it creates no durable Harness state. `harness doctor --database PATH` additionally inspects an explicitly selected, already initialized Harness database for supported schema state, WAL mode, foreign-key enforcement, and FTS5 availability. Database inspection does not create or migrate the selected path; a missing or invalid database is reported as a bounded failure. Even though the daemon now has a canonical database default, `doctor` intentionally requires `--database PATH` before inspecting durable state so the no-argument diagnostic stays runtime-only. The broader doctor contract (daemon, permissions, registrations, host adapters, projects, index state, skills, dashboard, and stale integrations) is not implemented yet.

The installed CLI exposes `harness scan [PATH] [--socket PATH]`. `PATH` defaults to the current directory and may be any directory inside a Git worktree. The CLI canonicalizes it locally, then the daemon resolves the Git worktree root, registers or reuses durable Project/Workspace identity as described above, and performs deterministic local non-LLM index reconciliation. The result reports Project/Workspace identity, whether either identity was newly created, effective visibility mode, canonical Workspace root, total indexed files, and added/updated/removed counts. Registry identity is durable state while the Structural Index is rebuildable derived state: if registration succeeds but a later reconciliation fails, the registered Workspace remains and a retry reuses it rather than inventing a second identity. With no `--socket`, the CLI validates/reuses the canonical per-user daemon and lazily starts it from the installed package when the local transport is unavailable, waiting for bounded readiness before the scan request. `--socket` remains an explicit development/recovery override and never triggers canonical daemon autostart.

The installed CLI also exposes `harness status [PATH] [--socket PATH]`. `PATH` defaults to the current directory and is treated as a filesystem location inside an already registered Workspace. The command resolves that location through the daemon's fail-closed Workspace resolver and prints only compact mechanical state: Project/Workspace identity, canonical root, visibility mode, Git branch/HEAD, dirty-path summary, indexed-file count, and schema version. It is read-only: it does not register a Project/Workspace, run a scan, or mutate the database. With no `--socket`, it validates/reuses the canonical per-user daemon and lazily starts it when the local transport is unavailable. A missing runtime directory is allowed only as a first-run state; once it exists, the client requires a real current-user-only directory before trusting the socket. Explicit `--socket` usage remains caller-managed and does not autostart the canonical daemon.

The installed CLI now also exposes `harness dashboard [--socket PATH]`. The command asks the selected daemon over the existing OS-user-only IPC channel to lazily start one read-only HTTP server bound to `127.0.0.1` on an ephemeral port, then prints the private capability-bearing URL. The server is owned by the daemon lifetime, disables access logging, and exposes no unscoped root page: the random URL path is created in daemon memory and is returned only through local IPC. The initial Projects overview shows each registered Workspace's Project identity, root, current/recent Task state, last activity, next step, live branch/dirty count, and indexed-file count; persisted Task text is HTML-escaped and responses use a restrictive CSP plus `no-store`. A missing or replaced Git Workspace is displayed as an unavailable live status without discarding its persisted Task/index information. This slice is intentionally read-only; Project/Task detail pages, search, Accept/Feedback/Cancel, and SSE remain later dashboard tasks.

On supported POSIX systems the canonical daemon database is `$XDG_STATE_HOME/harness/harness.db` when `XDG_STATE_HOME` is an absolute path, otherwise `~/.local/state/harness/harness.db`. The canonical socket is `$XDG_RUNTIME_DIR/harness/harness.sock` when `XDG_RUNTIME_DIR` is absolute, otherwise `<system temporary directory>/harness-<effective uid>/harness.sock`. Empty/relative XDG values are ignored. Before the default database is used, the final Harness state directory is created/validated as a real (non-symlink) current-user-only directory. The daemon similarly requires its final socket directory to be a real current-user-only directory before bind, so pre-created symlink entries in a shared temporary namespace fail closed.

The installed `harnessd` console script exposes `harnessd serve [--database PATH] [--socket PATH]`. With no overrides it initializes/migrates the canonical per-user database and binds the canonical per-user Unix-domain socket. The daemon serves global/Workspace status, compact Task-continuity status, bounded Workspace search, deterministic Workspace scan, Task start/resume/checkpoint requests, and lazy discovery/ownership of the read-only loopback Projects dashboard. Task writes remain explicit-identity/CAS operations; the MCP bridge never writes SQLite directly. The two path options remain available independently for development, tests, recovery, or isolated manual operation; concurrent isolated daemon instances require distinct selected Harness databases. On supported POSIX systems the socket directory must be a real directory owned by the current OS user with no group/other access. Harness holds process-lifetime `flock` ownership for both the selected socket endpoint (`<socket>.lock`) and the resolved selected database (`<database>.lock`), with both lock files secured to `0600`. The endpoint lock is acquired before stale-socket classification; the database lock is acquired before SQLite initialization/migration. A competing daemon therefore cannot reuse the endpoint or become a second writer for the same Harness database through another socket or an equivalent database path alias. If the endpoint lock is free after a crash, Harness removes an existing same-user Unix socket only when it cannot accept a connection and its device/inode identity is unchanged at unlink time; connectable sockets and non-socket/unsafe entries fail closed. Harness creates a missing final runtime directory with mode `0700`, sets the served socket to `0600`, removes only the socket inode it created on clean shutdown, and intentionally leaves the reusable lock files in place. These singleton rules also make concurrent lazy-autostart attempts safe: racing clients may launch more than one process, but only one can acquire the canonical endpoint/database ownership.

The global status result remains deliberately small: schema version plus Project and Workspace counts. `workspace_status` accepts at most four ordered absolute filesystem hints, resolves them against the durable Workspace registry with the existing fail-closed priority rules, verifies the registered Git identity, and returns only compact mechanical state: Project/Workspace identity, effective visibility mode, canonical Workspace root, live Git branch/HEAD, dirty-path count, and current indexed-file count. It does not expose source text, search results, Tasks, Knowledge, or MCP objects. `workspace_search` uses the same bounded hint contract, additionally accepts the bounded query and item limit, verifies registered Git identity around a consistent database read snapshot, and returns only Project/Workspace identity plus mechanical search hits. It never returns indexed content hashes or source content.

The current internal IPC protocol is independent of MCP wire objects, uses protocol version `1`, allows exactly one request/response per connection, enforces a 16 KiB message limit, uses bounded request/response timeouts, and rejects unknown fields/methods fail-closed. `dashboard_url`, `workspace_status`, `workspace_task_status`, `workspace_search`, `workspace_index_entry`, `scan_workspace`, `task_start`, and `task_checkpoint` are additive protocol-v1 methods; the original global `status` wire shape remains unchanged. The scan and Task clients use longer bounded receive timeouts for their bounded mechanical work. Canonical POSIX clients lazily start the daemon from the installed Python package when needed, with a three-second readiness bound and existing runtime-directory validation. Windows daemon IPC and canonical Windows transport paths remain unsupported until that separate platform task is proven.

The first skills slice now loads a canonical external registry from `~/.harness/skills`, keeps Harness applicability metadata in `harness.yaml` separate from portable `SKILL.md`, derives deterministic stack evidence from the current Structural Index plus supported manifests, and combines it with durable Task `stack_hints` and explicit resolver include/exclude policy under a bounded visible-skill budget. Projection planning models host compatibility roots so one active host profile sees one Harness copy or the operation fails closed; reconciliation mutates only exact Harness-owned generated skill directories, rejects tracked/user-owned collisions, rechecks target state immediately before mutation, and uses Git's own `rev-parse --git-path info/exclude` path without touching `.gitignore`. This is core automated projection proof, not a claim that proprietary hosts actually surface the generated skills yet.

The installed CLI also exposes `harness mcp`, implemented with the official `mcp==2.0.0` SDK and the MCP 2026-07-28 sessionless protocol path. It serves exactly `project_status`, `project_search`, `project_context`, `task_start`, and `task_checkpoint` over stdio and delegates durable state to `harnessd`. The stdio boundary rejects oversized or concurrently duplicated JSON-RPC request identities before dispatch and bounds every serialized outbound frame, so untrusted envelope fields cannot bypass model-facing byte budgets or trigger a Task mutation whose response cannot be correlated safely. Request-ID collision checks use the official SDK correlation semantics, so integer IDs and their stringified forms share one in-flight identity. A Harness-owned Claude Code registration marks the bridge with `HARNESS_HOST_PROFILE=claude-code`; for that profile the adapter uses Claude Code's documented `CLAUDE_PROJECT_DIR` as an exact Workspace-root hint and fails closed if it is absent. Generic/manual launches retain the existing `HARNESS_WORKSPACE_ROOT` exact-root override and otherwise use the current process directory as a location hint. `project_status` includes the current working Task, or the most recently updated relevant waiting Task, plus its latest checkpoint identity and `next_step`, so a new bridge process can resume the same durable Task using the returned `task_id` and `revision`. The current `project_search`/`project_context` implementation remains limited to bounded mechanical indexed-path references; `project_context` resolves those refs through an exact read-only daemon index lookup rather than reusing the shorter search-query contract. Richer semantic channels are not claimed yet.

Development uses `uv 0.12.5`. Install/sync exactly from the committed lock and run the repository quality gate with:

```text
uv sync --locked --all-groups
uv run --frozen python scripts/quality.py
```

Manual CLI/daemon work should use the repository-local runtime so development does not collide with a separately installed Harness build:

```text
scripts/dev sync
scripts/dev harness doctor
scripts/dev harness scan
scripts/dev harness status
scripts/dev stop
```

`scripts/dev` exports XDG state/runtime paths under `.harness/` and runs this checkout through `uv run`; see [`docs/development/isolated-development.md`](docs/development/isolated-development.md).

The quality gate checks lock freshness, formatting, lint, strict typing, pytest, and a wheel smoke test that installs the built artifact into an isolated environment, executes both shipping console scripts, verifies that installed CLI help exposes the implemented commands/runtime-path override contract including search, and runs the installed `harness doctor` command.
