# Harness

Harness is a local-first control plane for coding agents. It preserves project intelligence across agent sessions and hosts while keeping source editing, shell access, Git, and browsing in the native host.

> **Repository status:** implementation foundation. The supported POSIX/Linux local path now includes Claude Code and Cursor IDE/CLI MCP adapters, multi-host install/uninstall orchestration, exact Workspace-root resolution, duplicate-free shared skill projection, operational doctor checks, upgrade-safe daemon replacement, and installed-wheel cross-host continuity acceptance. Codex/Antigravity MCP integration, proprietary-host acceptance, richer structural/symbol retrieval, Working Sets, and optional embeddings remain later work. Durable Project/Workspace, Task/Knowledge, deterministic index, dashboard, and the official five-tool MCP bridge remain host-neutral core state.


## Product principles

- One global Harness installation, isolated project context.
- Native-agent-first integration through MCP.
- Progressive disclosure instead of bulk context dumps.
- Filesystem and Git remain sources of truth for code and repository state.
- Semantic knowledge is captured only after real task investigation and always has provenance.
- A small, stable model-facing surface: status, search, context, task start/resume, checkpoint.
- One modular-monolith core; host-specific behavior stays in adapters.
- Two explicit publication modes: Normal for ordinary native-host SCM behavior, Hidden for local-only agent integration with human-owned Git/SCM publication.

## Linux local use with Cursor

The primary Linux local close-out is Cursor IDE/CLI in Normal mode: `harness install --host cursor`. Claude Code and `harness install --host all` remain implemented. Omitting `--host` still selects `claude-code` for compatibility and is not the first profile this workstation path must close.

`uv tool install` of this repository requires `uv` 0.12.5. Checkout development uses the same version via `scripts/dev` (bootstrapped into `.harness/tools/uv` when needed). System `uv` 0.12.1 cannot install this repo.

```bash
uv tool install --python 3.13 .
harness install --host cursor
harness doctor
cd /path/to/git/repository
harness scan
# After Harness changes Cursor MCP config, fully quit and reopen Cursor.
agent mcp list
agent mcp list-tools harness   # expect exactly five Harness tools
harness status
```

Claude Code remains `harness install` / `harness install --host claude-code`. Both hosts together are `harness install --host all`. Current Claude Code `claude mcp get` absent-server text (quoted or unquoted) is classified as absent, so Claude CLI output drift is not a Cursor doctor/install/uninstall/scan blocker. Unexpected Claude inspect failures still fail doctor; true absence remains a warning.

Cursor's current official docs require a restart after editing `mcp.json`; Harness prints that restart/reopen reminder whenever install, scan, or uninstall actually changes Cursor MCP configuration. The Cursor CLI shares the editor MCP config, so `agent mcp list` and `agent mcp list-tools harness` are the preferred host-side inspection probes when the CLI is installed. These probes are not proprietary Cursor UI/CLI acceptance; that matrix in [`docs/host-compatibility.md`](docs/host-compatibility.md) remains unchecked.

Claude Code registration remains owned through the official `claude mcp` CLI and resolves the active Workspace from `CLAUDE_PROJECT_DIR`. Cursor uses `~/.cursor/mcp.json` globally plus a complete `.cursor/mcp.json` override for every registered Workspace; both pass Cursor's `${workspaceFolder}` as `HARNESS_WORKSPACE_ROOT`. Cursor IDE chat uses the user-level server (`user-harness`) and interpolates that variable from the current window's first workspace folder. The Cursor bridge profile accepts only that exact interpolated root hint instead of guessing from cwd or inherited folder-path environment. A missing or still-literal value lists no tools. `harness scan` detects all current supported Harness profiles and performs one compatible skill reconciliation, so Claude and Cursor do not receive duplicate Harness skills through Cursor's compatibility roots.

`harness uninstall --host claude-code|cursor|all` removes only selected Harness-owned host artifacts while preserving Project Intelligence and any other active host. The daemon remains alive while another supported host is active; `--purge` is refused in that state. Cursor project config that is tracked by Git is manual-adoption/manual-removal only, so Harness never creates a dirty tracked diff. `harness dashboard` and `harness skills list` remain host-neutral. Reinstall/update through another Python environment updates Cursor global and registered project overrides as well as Claude registration. See [`docs/release-linux.md`](docs/release-linux.md) and [ADR-0024](docs/decisions/0024-linux-cursor-multi-host-lifecycle.md). Cursor Cloud Agents are outside this local adapter contract.

## Development state

The repository now has a Python 3.13 package, a locked development toolchain, and SQLite schema version 11. Database initialization creates ordered migration metadata, requires WAL mode, enables foreign-key enforcement for Harness connections, probes FTS5 as a runtime capability, and migrates the bootstrap schemas forward without discarding unrelated existing data.

Schema v11 contains the durable Project/Workspace registry, the rebuildable `indexed_files` Structural Index slice, durable Task/CAS state, one-to-one mechanical Task baseline storage, immutable Task checkpoint/event history, bounded operator feedback attached to immutable Task events, and rebuildable FTS5 candidate indexes for Knowledge and Task semantic retrieval. Task rows remain Workspace-owned, use the minimal `working`/`waiting`/`completed`/`cancelled` states, require an allowed reason only while waiting, and carry a positive monotonic revision. A partial unique SQLite index enforces at most one distinct `working` Task per Workspace even if a caller bypasses normal domain checks. Existing-Task state transitions still require explicit `task_id` plus `expected_revision`; successful transitions increment revision exactly once, stale revisions are non-mutating, and completed/cancelled Tasks are terminal. Human review uses the same contract: Accept completes only a Task waiting for `operator_review`, feedback atomically persists bounded operator text and resumes that same Task, and cancel terminates an explicit non-terminal Task. Pending feedback is surfaced through `project_status` only while it is attached to the current working revision, then clears after the next checkpoint.

The baseline-aware internal creation path now atomically captures the required mechanical start state before committing a new Task at revision 1. A baseline records Git HEAD/branch, UTC timestamp, current persisted Structural Index count/digest, a direct read-only `index_is_fresh` comparison against a live deterministic inventory, and every pre-existing Git dirty path with porcelain status, rename/copy origin when present, and a SHA-256 state fingerprint. Regular-file fingerprints include local file bytes but persist only the digest; symlinks hash the target string without following it for content; missing paths use a sentinel. Dirty submodules/directories and other entries that Harness cannot completely fingerprint are explicitly marked `opaque` so later comparisons remain conservative instead of producing false confidence. Baseline capture samples Git state twice around live-index inspection, verifies Workspace/Git identity, has a finite deadline, and rolls back Task creation if capture fails.

The internal changed-file calculator now compares that durable baseline with a stable current Git/worktree sample without mutating Task state or consulting the Structural Index. Exact unchanged non-opaque pre-existing dirty records are excluded; new dirtiness, changed/cleaned pre-existing dirtiness, conservative opaque entries, and committed tree deltas since the baseline HEAD are included. Task-time rename/copy records contribute both destination and origin paths. The calculation shares a finite deadline across baseline-row streaming, Git identity, dirty-content fingerprinting, committed-tree comparison, and deterministic result merging, and it fails closed if Workspace/Git state changes during the read.

The checkpoint persistence layer applies a checkpoint only to the explicitly named `working` Task using `task_id` plus `expected_revision`. A successful checkpoint increments Task revision exactly once and atomically stores bounded summary/next-step semantics, checkpoint state/wait reason, cumulative mechanical changed paths since Task start, current Git HEAD/branch/dirty-path count, provenance-bearing Knowledge, and an immutable checkpoint timeline event. Stale writers and mechanical calculation failures are fully non-mutating. Public `task_start`/resume and `task_checkpoint` are exposed through bounded daemon IPC and the MCP bridge; verification records and bridge activity history remain later slices.

New Projects are created with the required `normal` visibility default. The low-level explicit registration primitive remains internal and requires an explicit Project identity plus an inspectable Git worktree; Harness stores the canonical worktree root and Git common directory reported by Git, treats repeat registration as idempotent, fails closed on incompatible root/Project identity, and rejects contradictory visibility policy for Workspaces sharing one Git common directory. Public scan registration reuses an already registered root, attaches a new linked worktree to the one unambiguous existing Project sharing its Git common directory, and creates a new Project for a Git checkout whose common directory is not registered. It does not infer logical Project identity across independent clones or expose visibility-mode transitions.

The first deterministic index slice inventories regular files and symlinks for one registered Workspace, stores only relative path, entry kind, byte size, and SHA-256 mechanical identity, and reconciles additions/changes/deletions transactionally. Candidate enumeration uses Git tracked/untracked state with standard Git ignores, `.harnessignore`, common generated-directory exclusions, and default sensitive patterns such as `.env`, PEM, and key files. Symlink targets are hashed as link metadata rather than followed for source content, and symlinked parent paths that escape the Workspace fail closed. The index is derived/rebuildable data. Daemon-backed scans carry a finite execution deadline; deadline expiry rolls back an in-progress index reconciliation. The POSIX daemon now runs a bounded background watcher that treats Git/filesystem observations only as invalidation hints, debounces changes, serializes with explicit scans, and always reconciles through the same deterministic `scan_workspace` path. Existing Workspaces receive an initial reconciliation after daemon restart, and a slower periodic full reconciliation repairs missed hints. The watcher does not add another source of truth or persist/return source contents; content hashing remains part of the authoritative reconciliation scan. This slice still does not parse symbols/languages or populate FTS.

The mechanical search slice performs deterministic, Workspace-scoped retrieval over current `indexed_files` rows without reading or returning source text. It ranks exact relative-path matches, exact filenames, normalized ASCII identifier-token matches (including common camel/snake/kebab/dotted forms), then case-insensitive path substrings. Queries are bounded to 256 UTF-8 bytes, result count is hard-bounded to 50 with a default of 10, and each hit exposes only relative path, entry kind, size, and the mechanical match reason. The installed CLI exposes this as `harness search QUERY [PATH] [--limit N] [--socket PATH]`. MCP `project_search` now adds daemon-owned Project Intelligence channels: current-Workspace `code:`/`doc:` refs plus Project-scoped `knowledge:` and durable `task:` history refs backed by local FTS5 candidate indexes. Knowledge freshness is explicit and `needs_revalidation` cards rank after fresh cards; Task results can identify the matching checkpoint/operator-feedback fragment. `project_context` expands only caller-selected refs, rereads authoritative durable rows, preserves the existing metadata-only code/doc contract, and fails closed on cross-Project identities. Raw source still remains a native-host read. Symbols/structural graph search, Working Sets, richer rank fusion, and optional embeddings remain later slices.

The installed `harness` CLI includes the complete supported Linux `harness doctor` boundary. Bare `doctor` is read-only and inspects SQLite/FTS5, canonical permissions/artifacts, Claude adapter and MCP ownership, the daemon's frozen runtime identity, database/schema state, registered Project/Workspace Git identity, deterministic index freshness, canonical/generated skills, dashboard subsystem state, and stale integrations under bounded live-Workspace deadlines. Index and generated-skill warnings distinguish inspection timeouts and doctor-budget truncation from Project `unavailable` Git/identity failures, and they name the affected Workspace. Warnings do not make the command fail; integrity/ownership/compatibility failures do. It never starts the daemon/dashboard, scans, registers, or reconciles state. `harness doctor --runtime-only` preserves the original ephemeral in-memory SQLite/FTS5 probe, while `harness doctor --database PATH` performs read-only inspection of one explicitly selected initialized database.

The supported Linux/POSIX installation lifecycle is exposed as `harness install|uninstall --host claude-code|cursor|all`. The primary local close-out is `harness install --host cursor`; omitted `--host` still preserves the previous Claude Code default. Install verifies SQLite/FTS5, host ownership, and the frozen daemon schema/version/interpreter/code identity before mutation. Cursor global/project JSON mutation preserves unknown content, rejects foreign same-name entries, and fails closed on tracked project config that would require a write. Scan reconciles all current host profiles together. Partial uninstall reconciles skills against the remaining profiles and keeps the daemon alive; uninstall of the last active host performs owned skill cleanup and clean shutdown. Project Intelligence is preserved unless `--purge` is explicitly requested, and purge is refused while another supported host remains active.

The installed CLI exposes `harness scan [PATH] [--socket PATH]`. `PATH` defaults to the current directory and may be any directory inside a Git worktree. The CLI canonicalizes it locally, then the daemon resolves the Git worktree root, registers or reuses durable Project/Workspace identity as described above, and performs deterministic local non-LLM index reconciliation. After the scan, Harness inspects the supported local host registrations: a current Cursor registration first reconciles that Workspace's complete `.cursor/mcp.json` override, then all current Harness profiles are passed together to one daemon-owned skill reconciliation. This lets Claude Code and Cursor share one compatible projection while absent, stale, or foreign registrations never authorize a host surface. The result reports Project/Workspace identity, whether either identity was newly created, effective visibility mode, canonical Workspace root, total indexed files, and added/updated/removed counts. Registry identity is durable state while the Structural Index is rebuildable derived state: if registration succeeds but a later host/skill reconciliation fails, the registered Workspace remains and a retry reuses it rather than inventing a second identity. With no `--socket`, the CLI validates/reuses the canonical per-user daemon and lazily starts it from the installed package when the local transport is unavailable, waiting for bounded readiness before the scan request. `--socket` remains an explicit development/recovery override and never triggers canonical daemon autostart.

The installed CLI also exposes `harness status [PATH] [--socket PATH]`. `PATH` defaults to the current directory and is treated as a filesystem location inside an already registered Workspace. The command resolves that location through the daemon's fail-closed Workspace resolver and prints only compact mechanical state: Project/Workspace identity, canonical root, visibility mode, Git branch/HEAD, dirty-path summary, indexed-file count, and schema version. It is read-only: it does not register a Project/Workspace, run a scan, or mutate the database. With no `--socket`, it validates/reuses the canonical per-user daemon and lazily starts it when the local transport is unavailable. A missing runtime directory is allowed only as a first-run state; once it exists, the client requires a real current-user-only directory before trusting the socket. Explicit `--socket` usage remains caller-managed and does not autostart the canonical daemon.

The installed CLI now also exposes `harness dashboard [--socket PATH]`. The command asks the selected daemon over the existing OS-user-only IPC channel to lazily start one HTTP server bound to `127.0.0.1` on an ephemeral port, then prints the private capability-bearing URL. The server is owned by the daemon lifetime, disables access logging, and exposes no unscoped root page: the random URL path is created in daemon memory and is returned only through local IPC. The Projects overview links into capability-scoped Project, Workspace, and Task detail pages. Workspace detail reuses the deterministic bounded indexed-path search contract and returns only path metadata; Task detail renders a bounded recent durable timeline of checkpoints/operator actions plus changed-path metadata without raw source. `Accept`, `Send feedback`, and `Cancel` still post through the exact same revision-CAS domain workflow and require exact same-origin browser metadata plus the rendered Task revision. Capability-scoped CSS/JavaScript assets allow a strict same-origin CSP without inline script/style. SSE is a bounded presentation-only freshness hint: an initial authoritative view fingerprint closes the render/connect race, then a persistent read-only SQLite connection watches `data_version` and emits only `ready`/`refresh`, never Task/source payloads; the browser delays reload when it would destroy unsaved feedback/search input. Persisted Task/feedback text is HTML-escaped, all responses remain `no-store`/`nosniff`/`no-referrer` without `Server`/`Date`, and missing/replaced Git Workspaces retain durable state while live status fails closed.

On supported POSIX systems the canonical daemon database is `$XDG_STATE_HOME/harness/harness.db` when `XDG_STATE_HOME` is an absolute path, otherwise `~/.local/state/harness/harness.db`. The canonical socket is `$XDG_RUNTIME_DIR/harness/harness.sock` when `XDG_RUNTIME_DIR` is absolute, otherwise `<system temporary directory>/harness-<effective uid>/harness.sock`. Empty/relative XDG values are ignored. Before the default database is used, the final Harness state directory is created/validated as a real (non-symlink) current-user-only directory. The daemon similarly requires its final socket directory to be a real current-user-only directory before bind, so pre-created symlink entries in a shared temporary namespace fail closed.

The installed `harnessd` console script exposes `harnessd serve [--database PATH] [--socket PATH]`. With no overrides it initializes/migrates the canonical per-user database and binds the canonical per-user Unix-domain socket. The daemon serves global/Workspace status, compact Task-continuity status, bounded Workspace search, deterministic Workspace scan, Task start/resume/checkpoint requests, and lazy discovery/ownership of the loopback Projects dashboard and its revision-CAS human review actions. Task writes remain explicit-identity/CAS operations; the MCP bridge never writes SQLite directly. The two path options remain available independently for development, tests, recovery, or isolated manual operation; concurrent isolated daemon instances require distinct selected Harness databases. On supported POSIX systems the socket directory must be a real directory owned by the current OS user with no group/other access. Harness holds process-lifetime `flock` ownership for both the selected socket endpoint (`<socket>.lock`) and the resolved selected database (`<database>.lock`), with both lock files secured to `0600`. The endpoint lock is acquired before stale-socket classification; the database lock is acquired before SQLite initialization/migration. A competing daemon therefore cannot reuse the endpoint or become a second writer for the same Harness database through another socket or an equivalent database path alias. If the endpoint lock is free after a crash, Harness removes an existing same-user Unix socket only when it cannot accept a connection and its device/inode identity is unchanged at unlink time; connectable sockets and non-socket/unsafe entries fail closed. Harness creates a missing final runtime directory with mode `0700`, sets the served socket to `0600`, removes only the socket inode it created on clean shutdown, and intentionally leaves the reusable lock files in place. These singleton rules also make concurrent lazy-autostart attempts safe: racing clients may launch more than one process, but only one can acquire the canonical endpoint/database ownership.

The global status result remains deliberately small: schema version plus Project and Workspace counts. `workspace_status` accepts at most four ordered absolute filesystem hints, resolves them against the durable Workspace registry with the existing fail-closed priority rules, verifies the registered Git identity, and returns only compact mechanical state: Project/Workspace identity, effective visibility mode, canonical Workspace root, live Git branch/HEAD, dirty-path count, and current indexed-file count. It does not expose source text, search results, Tasks, Knowledge, or MCP objects. `workspace_search` uses the same bounded hint contract, additionally accepts the bounded query and item limit, verifies registered Git identity around a consistent database read snapshot, and returns only Project/Workspace identity plus mechanical search hits. It never returns indexed content hashes or source content.

The current internal IPC protocol is independent of MCP wire objects, uses protocol version `1`, allows exactly one request/response per connection, enforces a 16 KiB message limit, uses bounded request/response timeouts, and rejects unknown fields/methods fail-closed. `dashboard_url`, `shutdown`, `runtime_diagnostics`, `workspace_status`, `workspace_task_status`, `workspace_search`, `workspace_index_entry`, `workspace_skills_reconcile`, `skill_cleanup`, `project_search`, `project_context`, `scan_workspace`, `task_start`, and `task_checkpoint` are additive protocol-v1 methods; the original global `status` wire shape remains unchanged. The release upgrader deliberately supports the immediately preceding protocol-v1 daemon that does not know `runtime_diagnostics`: only its structured `invalid_request` response activates a compatibility path that validates legacy `status`, requests the already-supported clean `shutdown`, and then verifies a newly started current-runtime daemon. Other diagnostics failures remain fail-closed. The scan and Task clients use longer bounded receive timeouts for their bounded mechanical work. Canonical POSIX clients lazily start the daemon from the installed Python package when needed, with a three-second readiness bound and existing runtime-directory validation. Windows daemon IPC and canonical Windows transport paths remain unsupported until that separate platform task is proven.

The first skills slice now loads a canonical external registry from `~/.harness/skills`, keeps Harness applicability metadata in `harness.yaml` separate from portable `SKILL.md`, derives deterministic stack evidence from the current Structural Index plus supported manifests, and combines it with durable Task `stack_hints` and explicit resolver include/exclude policy under a bounded visible-skill budget. Projection planning models host compatibility roots so every active host profile sees exactly one Harness copy or the operation fails closed; reconciliation mutates only exact Harness-owned generated skill directories, rejects tracked/user-owned collisions, rechecks target state immediately before mutation, and uses Git's own `rev-parse --git-path info/exclude` path without touching `.gitignore`. `harness scan` supplies the union of current Claude Code and Cursor profiles to that single planner. Partial uninstall recomputes projections for the remaining profiles, while uninstalling the final active supported host removes only Harness-owned generated projections before daemon shutdown. Automated fixtures and installed-wheel acceptance prove the shared projection mechanics; proprietary-host UI visibility remains acceptance-gated.

The installed CLI also exposes `harness mcp`, implemented with the official `mcp==2.0.0` SDK and the MCP 2026-07-28 sessionless protocol path. It serves exactly `project_status`, `project_search`, `project_context`, `task_start`, and `task_checkpoint` over stdio and delegates durable state to `harnessd`. Production launches with `HARNESS_HOST_PROFILE` list no tools and refuse calls when they resolve to the Harness source checkout's isolated-development overlay; the tracked `scripts/dev harness mcp` overlay without that profile marker still serves the five tools. A Cursor-profile process that did not receive an interpolated `HARNESS_WORKSPACE_ROOT` from `${workspaceFolder}` likewise lists no tools; that is the pre-install global `user-harness` server, not the intended post-install state. The stdio boundary rejects oversized or concurrently duplicated JSON-RPC request identities before dispatch and bounds every serialized outbound frame, so untrusted envelope fields cannot bypass model-facing byte budgets or trigger a Task mutation whose response cannot be correlated safely. Request-ID collision checks use the official SDK correlation semantics, so integer IDs and their stringified forms share one in-flight identity. A Harness-owned Claude Code registration marks the bridge with `HARNESS_HOST_PROFILE=claude-code`; for that profile the adapter uses Claude Code's documented `CLAUDE_PROJECT_DIR` as an exact Workspace-root hint and fails closed if it is absent. Generic/manual launches retain the existing `HARNESS_WORKSPACE_ROOT` exact-root override and otherwise use the current process directory as a location hint. `project_status` includes the current working Task, or the most recently updated relevant waiting Task, plus its latest checkpoint identity and `next_step`, so a new bridge process can resume the same durable Task using the returned `task_id` and `revision`. `project_search` now searches bounded current-Workspace code/docs plus Project-scoped durable Knowledge and Task-history semantic fragments. Candidate lookup uses local rebuildable FTS5 indexes, while model-visible results and `project_context` are reconstructed from authoritative index/Knowledge/Task tables under one daemon-owned Workspace→Project read boundary. `project_context` accepts only explicit bounded refs, preserves metadata-only code/doc expansion, exposes stale Knowledge as a historical clue rather than a current fact, and never returns stored source hashes or raw source. Working Sets, symbol/graph retrieval, and embeddings are not claimed yet.
