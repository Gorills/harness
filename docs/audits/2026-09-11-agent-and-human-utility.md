# Аудит полезности Harness для агента и человека

Дата: 2026-09-11. Проверенный checkout: `8364bce19912a9b7bb413d0d2a6d6c4124e81844`.
Область: поиск, задачи, dashboard, качество и доставка скиллов, определение стеков,
потребности проекта `server-monitoring`. Это аудит и предложение порядка исправлений,
а не изменение действующих архитектурных правил.

## Вывод

Жалобы имеют конкретные основания. Некоторые готовые результаты поиска теряются на IPC;
поиск истории пропускает существующие задачи; правила сами поощряют дробление работы;
dashboard скрывает результаты проверок и часть истории; управление скиллами не объясняет,
что действительно получит агент. Обнаружены также ошибки применения политики скиллов.

Основа Harness пригодна для развития: единое durable-состояние, явная идентичность Task,
защита от устаревших записей, локальный поиск, разделение daemon/host и осторожная проекция
скиллов. Переписывать всё оснований нет. Приоритет — надёжность результата, уменьшение
числа обязательных действий и проверяемая польза в реальных сценариях.

## Метод и границы доказательств

- Прочитаны архитектура, исходная спецификация, аудит 2026-08-21 и относящиеся к подсистемам
  ADR, реализации и тесты. Три независимых направления проверки использовали одну общую
  Harness Task; отдельные задачи на каждую проверку не создавались.
- Выполнены живые MCP-запросы и отдельные воспроизведения на текущем checkout с временными
  Git/SQLite fixtures. Так отделены наблюдения работающего экземпляра от доказательств в коде.
- Проверены описания и тела всех 16 встроенных скиллов, выборочно их подробные references,
  структура проекции и фактические файлы скиллов в `server-monitoring`.
- Реальные серверы не опрашивались; скрипт мониторинга не исполнялся. Содержимое `.env`,
  SQL dump не читалось; canonical per-user state напрямую через файловую систему
  не читалось. Host-конфиги и проект мониторинга не менялись.
- Browser оказался недоступен. Выводы о dashboard основаны на коде, HTTP-тестах и
  синтетическом HTML-rendering. Визуальная оценка и интерактивные сценарии в браузере
  **не проверены**. Оценку «красиво/некрасиво» этот аудит не выдаёт за измеренный факт.
- Новые запуски слабой модели в Cursor не выполнялись. Риски формулировок скиллов
  отделены ниже от воспроизведённых дефектов программы.

## 1. Поиск

### S1. Часть корректных результатов отвергается IPC — исправить первой

Живой `project_search(query="task_start", scope="code", limit=3)` возвращает
`daemon symbol relation does not match the IPC schema`; повтор даёт ту же ошибку.

Временный Python-проект из `src/service.py` с определением `task_start` и
`src/caller.py` с импортом/вызовом даёт два результата в `read_project_search`.
Сериализация navigation и чтение её текущим IPC parser воспроизводят ошибку.
Для TypeScript определение также находится, но IPC отвечает
`daemon symbol navigation precise language is unsupported`.

Причина: [`ProjectSymbolRelation.to_wire`](../../src/harness/retrieval.py#L255)
добавляет поля `resolved_target`, `resolution_kind` и сведения об определении, а
[`ipc.py:3044`](../../src/harness/ipc.py#L3044) допускает только старые девять полей.
Кроме того, [`ipc.py:3011`](../../src/harness/ipc.py#L3011) принимает только `("python",)`.
Это дефект текущего checkout; переиндексация сама его не исправит.

Приёмка: реальные daemon → IPC → MCP roundtrip для всех поддерживаемых языков, пустых
и заполненных optional-полей, ограничений размера и недопустимых полей. Сохранить строгую
валидацию и negative-disclosure; не исправлять проблему бесконтрольным принятием любых ключей.

### S2. Одна длинная Task может вытеснить другие найденные Task

`_task_hits` сначала ограничивает SQL-выборку **фрагментов**, затем группирует их по Task:
[`retrieval.py:1611`](../../src/harness/retrieval.py#L1611). При лимите dashboard 24 верхняя
граница кандидатов — 384 фрагмента. В fixture две задачи содержат `needle`, но у первой
400 совпадающих checkpoints. Результат содержит одну задачу, хотя индекс подтверждает две.

Приёмка: ограничивать/добирать уникальные задачи, сохраняя релевантный фрагмент;
добавление checkpoints одной Task не должно скрывать другую совпадающую Task.
Сохранить project/workspace scope и бюджет ответа.

### S3. Задачу нельзя найти по её ID

Для существующей Task поиск полного ID и короткого префикса возвращает `[]`, поиск
названия работает. `task_id` и `fragment_ref` в FTS — `UNINDEXED`
([`storage.py:957`](../../src/harness/storage.py#L957)); отдельного ID lookup в
[`_task_hits`](../../src/harness/retrieval.py#L1587) нет. Dashboard при этом показывает
короткий ID ([`dashboard.py:1990`](../../src/harness/dashboard.py#L1990)).

Это недостающая возможность навигации, а не повреждение БД. Приёмка: полный ID и
однозначный префикс находят нужную задачу; неоднозначный префикс не выбирает случайную;
межпроектная изоляция сохраняется.

### S4. Естественный русский запрос ненадёжен

В fixture `задач` находит «Исправить поиск задач» и «Управление задачами», а `задачей`
не находит ни одной. Используется небольшой список окончаний и FTS-префиксы
([`search_text.py:81`](../../src/harness/search_text.py#L81),
[`search_text.py:247`](../../src/harness/search_text.py#L247)).
В живом запросе `где реализован поиск по проекту`, scope `code`, среди результатов —
`dashboard_i18n.py` и dashboard-тесты. Наличие текста запроса в UI не равно нахождению
реализации. Наблюдение конкретного ранжирования относится к проверенному индексу.

Начать с корпуса реальных RU/EN вопросов и ожидаемых файлов/Task. Проверять точные
идентификаторы, словоформы, цитаты, смешанный язык, отсутствие результатов, шум от тестов
и UI-строк. Затем менять нормализацию и ранжирование. Векторный поиск сам по себе
не исправит S1–S3 и пока не обоснован как первый шаг.

### S5. Проверяется использование поиска, но недостаточно его полезность

[`eval_search_behavior.py:387`](../../scripts/eval_search_behavior.py#L387) считает ответ
с current-source evidence сильным сигналом для классификации поведения агента. Это
не оценка семантической релевантности результата вопросу. Domain-тесты новой навигации
также не заменили roundtrip-проверку S1.

Нужны две отдельные оценки: корректность контракта и способность найти нужный материал
с меньшими затратами. Метрики: попадание нужного результата в top-5, доля ложных пустых
выдач, время до полезного файла, дополнительные native-поиски, ошибки и объём контекста.

## 2. Задачи и накладные расходы агента

### T1. Дробление работы предусмотрено инструкциями

[`ADR-0038`, Decision 4](../decisions/0038-task-required-for-diagnosis-and-schema-retry.md)
требует завершить/отложить текущую Task и создать новую при новом запросе оператора
или переходе диагностика → реализация. То же включено в
[`mcp_bridge.py:70`](../../src/harness/mcp_bridge.py#L70). Значит, даже корректно следующий
правилам агент может разбить одно исправление на несколько Task.

При этом исходная спецификация §2.4 требует, чтобы правильный путь был самым дешёвым,
а архитектура оптимизирует малое число ритуальных вызовов. Между целью и текущим
workflow есть продуктовое противоречие; ужесточать текст дальше недостаточно.

Предлагаемая единица: **один пользовательский результат — одна Task**. Диагностика,
исправление, проверки и уточнения того же результата остаются этапами/checkpoints.
Новую Task создавать при новой самостоятельной цели. Это предложение требует изменения
ADR и согласованных host-инструкций; данный аудит действующие правила не отменяет.

Не заменять это автоматическим слиянием похожих названий или записью в «текущую Task»:
сохранить явные `task_id`, CAS revision и защиту разных целей от смешивания.
Повторный resume уже работающей Task идемпотентен
([`task_workflow.py:80`](../../src/harness/task_workflow.py#L80)) — этот механизм стоит сохранить.

### T2. Обязательные действия имеют реальную стоимость, но выигрыш не измерен

Даже небольшая диагностика требует status → start/resume → checkpoint.
Создание Task также захватывает Git/index baseline
([`tasks.py:273`](../../src/harness/tasks.py#L273),
[`task_baseline.py:107`](../../src/harness/task_baseline.py#L107)). Это не просто запись названия.
Аудит не измерял latency на репрезентативных размерах проектов и не утверждает конкретное
замедление. Нужен сравнительный прогон одинаковых сценариев с Harness и без него:
качество результата, количество Task, tool calls, контекст и время.

Первый критерий: один баг, диагностика, исправление и два уточнения создают одну Task,
сохраняя историю и продолжение работы. Отдельно оценить, оправдана ли durable Task для
каждой краткой read-only проверки; не вводить новое исключение без измерения поведения моделей.

Нужно разделить: обнаруженные технические признаки, пользовательскую область работы,
выбранный набор, факт записи на диск и факт обнаружения хостом. Сейчас dashboard
получает только policy ([loader](../../src/harness/dashboard.py#L531),
[панель](../../src/harness/dashboard.py#L1225)); «Авто» не объясняет результат.
Policy сохраняется до reconciliation; ошибка доставки уходит в retry, а HTTP выглядит
как обычное успешное сохранение ([dashboard.py:925](../../src/harness/dashboard.py#L925)).

Панель должна показывать для каждого skill: почему выбран, от какого файла/настройки,
в какой Workspace и host root доставлен, состояние/ошибку reconciliation, доступ к тексту.
Отдельно обозначать, что файловая проекция не доказывает загрузку в уже открытую сессию.
Policy сейчас Project-scoped и действует на все его Workspaces — это должно быть видно.

Шесть общих skills нельзя выключить этим UI по [ADR-0045](../decisions/0045-project-skill-scope-policy.md).
Все совпавшие skills доставляются без count cap по ADR-0044. Это продуктовые решения,
а не ошибки переключателей. Не лечить нерелевантность произвольным обрезанием количества:
так можно потерять нужный skill. Сначала исправить evidence, scope и объяснение выбора.

Сохранить существующую защиту проекций: user-owned/tracked collisions, cleanup только
Harness-owned файлов, проверку ownership перед изменением, rollback и общий `.agents/skills`
для совместимых профилей. Эти механизмы имеют содержательные automated tests.

## 5. Качество скиллов и работа слабой модели

Тексты в целом содержат полезную инженерную дисциплину: локальный контракт важнее
предпочтений модели, минимальный объём изменения, сохранение данных/совместимости,
проверка фактического результата, честное описание непроведённых проверок. Тела большинства
skills короткие, детали вынесены в references. Это стоит сохранить.

Но **корректный текст ≠ доказанное улучшение поведения модели**. Часть quality-тестов
проверяет наличие фраз ([test_builtin_skills.py:349](../../tests/test_builtin_skills.py#L349)).
Codex acceptance проверяет чтение skill по nonce и выбор описания; это не оценка качества
администрирования или исправленного кода. Для Cursor в
[host-compatibility](../host-compatibility.md#cursor-native-skill-selection-manual-real-host)
описана отдельная ручная процедура. Этот аудит её не выполнял.

Оценка содержания и границ:

| Skills | Что полезно | Что проверить/улучшить |
| --- | --- | --- |
| `testing-strategy`, `legacy-preservation` | Регрессии, существующие контракты, честная verification | Стоимость обязательного чтения/проверок на маленькой правке; testing-текст объединяет publication и merge gates, тогда как инструкции Harness различают эти этапы. Сделать приоритет правил и масштаб проверки яснее. |
| `complex-change-planning`, `project-architecture` | Границы подсистем, миграции, запрет необоснованной архитектуры | Отрицательные сценарии: обычный фикс не должен превращаться в архитектурный аудит. Не дублировать управление Task в нескольких текстах. |
| `language-engineering`, `data-integrity` | Выбор версии/toolchain, транзакции, совместимость, сохранность | Проверять реальное покрытие языка, а не только доставку общего entrypoint. Например, Dart определяется стеком, но в language-entrypoint отдельного Dart-reference нет. |
| `secure-by-design`, `ci-release` | Конкретные границы данных, прав и поставки | Не активировать все глубокие references на всякий случай; оценивать применение нужной инструкции к реальному изменению. |
| `container-infrastructure`, `deployment-operations`, `observability` | Изоляция проекта, runtime evidence, rollback, метрики без неограниченной размерности | Сейчас преимущественно инструкции по изменению систем, а не полный workflow диагностики и сопровождения серверов. Не навязывать разработку контейнерного проекта при проверке чужого сервиса. |
| `public-frontend`, `frontend-design` | Семантика, работа со сложившимся дизайном, проверка рендера | У design-entrypoint обязательный пятичастный контракт и чтение guides для любой UI-задачи; это риск лишней работы на маленькой правке. Проверить краткий режим, отрицательные triggers и частные UI. |
| `server-application`, `mobile-application`, `godot-development` | Предметные lifecycle/платформенные ограничения | Проверять выбор только затронутых режимов, соответствие фактическому стеку и отсутствие чужих требований. |

Это редакторские риски и пробелы покрытия, **не измеренный процент ошибок слабой модели**.
Не усиливать весь pack дополнительными абсолютными запретами по каждому единичному сбою.

Нужен небольшой версионируемый корпус практических заданий. Одинаковые исходники и
критерии, несколько повторов на конкретной модели/версии Cursor, сравнение без Harness,
с текущим набором и с кандидатом. Оценивать результат и действия, а не упоминание skill.

Минимальные сценарии: маленький баг без рефакторинга; продолжение задачи после перезапуска;
уточнение без новой Task; пустой/сломанный поиск с разумным восстановлением; backend-only
правка в monorepo; небольшой UI-фикс; серверный инцидент только с диагностикой;
изменение checker с сохранением индивидуальных настроек хостов. Проверять выбор скилла,
необходимые evidence, лишние действия, scope, число Task/tool calls и качество результата.
Production-сценарии сначала моделировать на fixtures и записанных ответах инструментов.

## 6. Что нужно `server-monitoring`

Фактический локальный набор: 6 baseline skills, `data-integrity`, `container-infrastructure`.
`observability` и `deployment-operations` в `.agents/skills` отсутствуют.
Есть пользовательский `.cursor/skills/vps-host-alerts/SKILL.md`. Он предметный и полезный,
но description **явно исключает** общую диагностику серверов, падения сайтов и PM2/nginx/disk
инциденты. Поэтому он по своему контракту не закрывает запрошенное администрирование.
Его нахождение в общем skill-каталоге других хостов этим аудитом не доказано.

По именам файлов и безопасному структурному разбору checker видны Python, cron,
systemd/PM2/nginx/Docker-проверки и доставка алертов. Наличие Python и SQL dump описывает
технику хранения, но плохо выражает назначение проекта. Synthetic mirror
`host-alerts.py` + `host-alerts.cron` + `dump.sql` выбирает 6 baseline + `data-integrity`,
без observability/deployment/container. Причина фактически существующей container-проекции
не установлена: сохранённая policy, предыдущая проекция или версия runtime не проверялись.

Предлагаемый минимальный предметный набор:

1. Сохранить пользовательский `vps-host-alerts` как руководство именно checker.
   Не переписывать его и не переносить между каталогами без отдельной проверки ownership
   и host visibility.
2. Добавить один `server-operations` skill: диагностика → гипотеза → минимальное действие
   в рамках запроса → проверка пользовательского симптома → rollback/продолжение.
   References раскрывать по задаче: Linux-сервисы/ресурсы, сеть/DNS/TLS, диски/данные и
   восстановление, мониторинг/алерты. Это предложение, файлы не создавались.
3. Использовать существующие `observability` и `deployment-operations` по назначению;
   containers — только для относящихся к ним работ. Python/data guidance нужно при
   изменении checker/данных, а не как замена эксплуатации.
4. Дать человеку явную область «Эксплуатация серверов» и объяснение выбора. Автоопределение
   использовать как подсказку с evidence, а не угадывание роли проекта по расширению `.py`.

Простое добавление ещё одного skill поверх неизменного набора не решит проблему лишних
инструкций. Для ops-профиля отдельно обосновать состав общей основы и разделить её
релевантность эксплуатации и изменению программ. Если потребуется отказаться от
неотключаемых шести baseline skills, это явное изменение ADR-0045, проверяемое сравнением
сценариев, а не скрытая особенность нового переключателя.

Серверные адреса, секреты, конкретный inventory и runbook остаются в пользовательском
проекте; универсальный skill не должен вшивать их в общий pack. Он должен различать
диагностику и изменение, учитывать уже данное разрешение, не добавлять рутинных повторных
подтверждений. Развёртывание по всем серверам не выводить из просьбы проверить один.

Приёмка: «сайт недоступен» приводит к локализации причины по наблюдениям, не к массовому
restart; ложный алерт отделяется от реального отказа; изменение checker сохраняет
индивидуальные host settings; проверка доставки не посылает незапрошенные тестовые алерты;
секреты не попадают в вывод. Сначала изолированные сценарии, затем отдельно реальная
host acceptance при разрешённом доступе.

## 7. Порядок исправлений

Это порядок независимых изменений, не новые Task и не разрешение на реализацию.
Каждый следующий кандидат должен оставлять проект работоспособным.

| Очерёдность | Изменение | Условие завершения |
| --- | --- | --- |
| 1 | Исправить S1: согласовать navigation serializer/IPC/MCP | Roundtrip всех поддерживаемых языков и optional-полей проходит; живой проблемный запрос работает после штатного обновления runtime. |
| 2 | Исправить поиск Task: уникальные кандидаты, ID, русские запросы | Fixtures S2–S4 проходят; корпус реальных запросов имеет записанный baseline и улучшение без регрессий точного поиска. При необходимости разделить backend полноты и ранжирование на два изменения. |
| 3 | Пересмотреть ADR-0038 и bootstrap вокруг одного результата | Уточнения и диагностика→исправление не размножают Task; CAS/continuity сохранены; проверено на целевой слабой модели. |
| 4 | Вернуть достоверность dashboard | Verification видна, счётчики считают Task, история доступна полностью, ошибки сохраняют ввод. Каждый из этих дефектов можно исправлять и проверять отдельно. |
| 5 | Исправить skill-policy и сделать доставку понятной | Excluded/Included проходят перекрёстную матрицу; видны выбранный pack, evidence, фактическая проекция и её ошибки. |
| 6 | Исправить stack scope и ops coverage; подготовить `server-operations` | Fixtures подпроектов/конфигов/примеров проходят; `server-monitoring` получает объяснимый предметный набор без лишних доменов. |
| 7 | Переработать dashboard по рабочим сценариям; отредактировать pack по eval | Проверены реальные размеры/ввод/SSE/навигация. Кандидат скиллов улучшает результат и/или снижает цену работы на согласованном корпусе. |

Корпус сценариев нужно начать собирать сразу; он является проверкой всех этапов,
а не заключительной декоративной метрикой. Изменения Task-политики, scoped detection
и деградации при невалидном manifest потребуют ADR. После изменения конфигурации Harness
действующие правила требуют полного перезапуска хоста и новой Task; текущий snapshot
инструкций сам не обновится.

Уточнение после реализации пункта 3: требование «новой Task» выше описывает исходный
снимок правил аудита. Поправка от 2026-09-11 в
[ADR-0038](../decisions/0038-task-required-for-diagnosis-and-schema-retry.md) различает
новую беседу хоста и долговечную Harness Task: после фактического обновления конфигурации
хост полностью перезапускается, а незавершённая Task того же результата продолжается по ID.
Исходный код доставки и продолжение через MCP проверяются автоматически;
[приёмка на целевой слабой модели](../development/task-continuity-acceptance.md)
пока не выполнена. Это не закрывает всю приёмку пункта 3.
