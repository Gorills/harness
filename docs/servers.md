# Общий реестр серверов

В Dashboard откройте «Серверы»: карточки и история доступны без зарегистрированного проекта.
У одного сервера может быть несколько связей с проектами. ID остаётся постоянным; архивирование
сохраняет карточку и историю. Пароли и приватные ключи остаются в отдельном личном хранилище.
Реестр содержит SSH-алиас, пользователя, порт и ссылку на ключ, но не содержимое ключа.

Следующая модель карточек спроектирована в [Карте сервера и приложений](server-map-design.md):
полные списки приложений, доменов, каталогов, служб и сертификатов с проверяемыми связями.
Документ имеет статус предложения; ниже описано действующее поведение.

В списке серверов доступны поиск по серверу, приложению, адресу или домену, фильтр окружения
и переключатель «Активные / Архив». Название открывает карточку; «Добавить сервер» раскрывает
форму над списком. На узком экране адреса и домены располагаются под названием сервера.

Карточка разделена на четыре вкладки:

- **Обзор** — паспорт машины, назначение, адреса, поля подключения SSH, сервисы, пути и правила работы.
  Паспорт отдельно показывает ОС и ядро, процессор и число логических CPU, общий объём памяти,
  swap, диски и размещение у провайдера. «Заполнить паспорт» / «Редактировать паспорт» открывает
  отдельную форму: её сохранение не меняет приложения, остальные сведения или прежнюю историю.
  Неизвестные значения видны как «Не указано», нулевой swap — как «Не выделен».
  Наблюдения проверок сгруппированы по системе, оборудованию, ресурсам, службам, доступу,
  сети и ограничениям, с датой снимка и одним раскрываемым источником на набор наблюдений.
  Непроверенные сведения свернуты в явно обозначенные блоки. Старые заметки группируются только
  при отображении по известным заголовкам; их текст, дата и источник не переписываются.
  «Редактировать сервер» раскрывает форму, сгруппированную по назначению полей.
  Источник сведений, постоянный ID, связи с проектами и архивирование находятся в блоке
  «Источник, идентификаторы и архив».
- **Приложения** — название, домен, стек и окружение каждого приложения. Раскройте строку
  для просмотра сведений, затем «Редактировать приложение» для изменения. Поиск и страницы
  сохраняют контекст выбранного сервера.
- **Профили подготовки** — правила размещения и подготовки площадок. Сведения профиля
  просматриваются отдельно от его редактора.
- **История** — журнал работ и отдельная форма «Добавить запись».

Вкладки переключаются без перезагрузки и сохраняют незаписанные формы. Ссылка с фрагментом
(`?sites_q=example#server-sites`, `#server-history`) открывает нужный раздел; «Назад» и «Вперёд»
восстанавливают вкладку. Без JavaScript все разделы остаются доступны на одной странице,
а раскрываемые редакторы и обычные формы продолжают работать.
Поиск обновляет результаты на месте. Если новый результат уберёт форму с незаписанным
черновиком, текущий экран сохраняется и предлагает сначала сохранить данные. Ошибка поиска
также сохраняет введённый запрос и формы; поиск не повышает ревизию соседнего черновика.

Если Dashboard не получил обновление, он показывает «Не удалось обновить», сохраняет формы
и черновики; повторите «Обновить» после восстановления соединения. После неподтверждённого
сохранения обновление остаётся чтением: проверьте результат перед повторной отправкой формы.

## Очистка истории по прямому запросу оператора

Обычная история дополняется, но не редактируется. Исключение — явная операторская очистка
всей истории одной выбранной карточки через установленный CLI:

```sh
harness servers clear-history SERVER_ID --expected-revision CURRENT_REVISION --confirm
```

Сначала получите точный ID и текущую revision карточки. `--confirm` подтверждает необратимое
удаление всех её событий, включая события реестра. При конфликте revision ничего не удаляется:
перечитайте карточку и согласуйте изменившееся состояние, не повторяйте запись автоматически.
Daemon удаляет события и увеличивает revision в одной транзакции, сохраняя карточку,
сайты, профили, связи с проектами и остальные серверы. Нового события очистки не создаётся.
Команда не удаляет серверные логи и не меняет удалённый сервер; она не доступна через пять
агентских MCP tools. Аудит, поиск карточки и правило об отсутствии следов исполнителя сами
по себе не разрешают очистку. Нужен прямой запрос оператора на эту историю.

## Общее правило деплоя для всех серверов

Сохраняйте принятую оператором схему деплоя. Имена и теги образов приложения должны совпадать
с публикацией CI; имя ветки само по себе не определяет тег. Обновление выполняется через
`docker compose pull`, затем `docker compose up -d`, с прежними Compose project, файлами и окружением.
Не заменяйте тег на `@sha256`, не закрепляйте плавающий тег, не подменяйте образ и не меняйте
схему CI, автоматизацию выкладки или процедуру отката по собственной инициативе. Любое отклонение
сначала конкретно опишите и согласуйте с оператором. Разрешение на подготовку, выкладку или ремонт
сервиса не означает согласия изменить эту схему. Читать digest для проверки образа разрешено.

Правило находится в исходниках встроенных skills `server-operations` и `deployment-operations`;
глобальная доставка `server-operations` делает его доступным также в чатах без проекта.

## Свежие уязвимости при диагностике и аудите

Глобальный `server-operations` требует при каждой инфраструктурной диагностике и аудите
сразу искать актуальные уязвимости фактически обнаруженного стека: ОС/ядра, служб, веб-сервера,
PHP и других runtime, расширений, СУБД и контейнерной среды в проверяемой области.
Поиск выполняется в интернете на дату проверки по бюллетеням производителей и security tracker
дистрибутива. Окно свежих публикаций — минимум 30 дней либо весь период с последней подтверждённой
проверки, если он больше. Дополнительно проверяются более старые неисправленные уязвимости
обнаруженных версий и сведения об эксплуатации. Указанная оператором дата служит ориентиром поиска,
а не подтверждением существования конкретного CVE.

Применимость проверяется по полной версии пакета/build, исправлениям дистрибутива, конфигурации
и доступности сервиса; один старый upstream-номер не доказывает уязвимость. Результат содержит
дату и охват проверки, CVE/бюллетень, даты публикации/обновления, затронутую и исправленную версии,
критичность, факты применимости, сведения об эксплуатации, приоритет действий и ссылки.
Подтверждённые проблемы, предположения и подтверждённые исправления различаются явно.
При недоступности поиска или неизвестной версии проверка помечается незавершённой; отсутствие
найденных CVE не объявляется доказательством безопасности сервера.

Это обязательная часть диагностики, но не разрешение на эксплуатационные пробы, обновления
или перезапуски. Простое чтение реестра и диагностика кода/SQL/бизнес-данных сами по себе
не превращаются в аудит сервера и не разрешают запись в его историю.

## Доступ агентов без папки

После установки новой версии Harness выполните из установленного runtime:

```sh
harness servers setup --host codex
```

Команда запускает daemon, добавляет отдельное глобальное подключение `harness-servers` в
`$CODEX_HOME/config.toml` (по умолчанию `~/.codex/config.toml`) и пользовательский skill
`~/.agents/skills/server-operations/SKILL.md`. Чужие MCP entries и настройки сохраняются;
коллизии и изменённые файлы требуют ручного согласования. Настройка никогда не переносит vault.
При сбое настройки или удаления Harness восстанавливает прежнюю регистрацию, skill и маркер
владения, если файлы по-прежнему содержат изменения этой команды. Конкурентные правки оператора
сохраняются при обнаружении; если полный откат невозможен, ошибка явно требует ручного согласования.
Параллельные setup/remove используют общие locks для skill и Codex config/маркера, удерживая их
от чтения до завершения или отката. Если locks не удаётся получить за 5 секунд, команда завершается
без изменения этих файлов и предлагает повторить попытку. Постоянные `.harness-servers.lock` в `$CODEX_HOME`
и `$HOME/.agents/skills` остаются после завершения; не удаляйте их во время работы других команд.
Неизвестные или ссылочные lock-файлы требуют ручного согласования и не перезаписываются.
Перед заменой файлы повторно проверяются после записи и fsync временного файла, перед удалением —
сразу перед unlink. Это не атомарный CAS против стороннего редактора, игнорирующего locks:
между последней проверкой и изменением остаётся короткое окно. Несколько файлов также не образуют
единую crash-atomic транзакцию.
Затем полностью перезапустите Codex и откройте новый чат без проекта. Текущий чат не получает
новые инструменты автоматически. После перезагрузки компьютера запустите `harness servers start`,
если daemon ещё не работает. Глобальное HTTP-подключение само по себе не запускает daemon.

```sh
harness servers start
harness servers list
harness servers setup --host codex --remove
```

Global-only skill входит в канонический реестр (`harness skills sync`), но не выбирается по
стеку каждого проекта. Не добавляйте его одновременно в project includes, если используете
пользовательскую доставку: Codex может показать два skills с одинаковым именем.
Project MCP `harness` остаётся отдельным и по-прежнему требует точный Workspace header.
Работа без папки не даёт права читать связанные репозитории или выполнять SCM в Hidden.

В исходном checkout команды runtime выполняются через `scripts/dev`. Global setup здесь
запрещён; синтетические тесты адаптера используют временные home/CODEX_HOME и не меняют ваши
настройки. Live activation новой версии — отдельная операторская операция установки.

## Импорт существующего server-monitoring

Сначала preview индекса (не читает карточки):

```sh
harness servers import /path/to/server-monitoring
harness servers import /path/to/server-monitoring --apply
```

Preview показывает только разрешённые поля: имя, alias исходного ID, SSH пользователь/порт,
адрес, домены и происхождение. Применение создаёт новые записи, а существующие сохраняет.
Каждый source ID получает стабильный `srv-…` ID; домены не служат основанием слияния хостов.
Неизвестные домены без карточки не становятся выдуманными серверами. `checked_at: null`
означает неизвестную актуальность, даже если source был недавно импортирован.

Для контекста конкретного сервера выберите одну карточку:

```sh
harness servers import /path/to/server-monitoring --server source-id
harness servers import /path/to/server-monitoring --server source-id --apply
```

Импорт читает только `host-source-id.mdc`. Из секций Frontend, Services/Сервисы,
основной backend/фоновые задачи, Strapi CMS, Nginx/TLS, Resources/автозапуск и Paths/Важные
пути он извлекает известные имена сервисов и абсолютные пути в inline-code. Строки с секретами,
env и дампами пропускаются. Произвольные правила/команды, учетные данные, содержимое конфигов,
SQL и инструкции резервного копирования не импортируются. Эти сведения проверяются отдельно
по выбранной карточке и текущему состоянию; отсутствие секции остаётся незаполненным полем.

Если индекс уже импортирован, выбранное обогащение по умолчанию тоже сохраняет существующую
запись. Для добавления ссылок к существующей карточке получите её текущую ревизию и явно передайте:

```sh
harness servers import /path/to/server-monitoring --server source-id --apply --expected-revision 1
```

Это CAS merge сервисов/путей/общих правил с сохранением полей оператора и записью источника как
непроверенного факта. При конфликте перечитайте карточку и согласуйте новую запись. Исходный
репозиторий не изменяется. Повторный import не перезаписывает уже редактированные записи.

## Контракт MCP

`/servers/mcp` требует bearer capability текущего локального пользователя и не требует Workspace.
`server_list(query, archived, environment, limit, offset)` ищет имя сервера/приложения, alias, адрес и домен, показывает
неоднозначность и страницу. `server_get(server_id, history_limit, before)` выдаёт одну карточку,
ревизию и историю; `next_before` позволяет читать более ранние записи.

Все записи требуют явные `server_id` и `expected_revision`. Для существующего сервера `server_save`
принимает ровно одну операцию: частичный patch базовых `metadata`, целый `site` или `profile`,
`delete_site_id` или `delete_profile_id`. Базовый patch сохраняет пропущенные поля и отвергает
`sites`/`platform_profiles`: соседние записи сохраняются атомарно при отдельной операции с child. Для создания
используйте chosen stable ID и ревизию 0. `server_archive(..., archived)` архивирует/восстанавливает.
`server_record(..., event)` добавляет результат с kind=`audit|operation`, summary, findings,
source и timezone-aware ISO checked_at. Через MCP историю нельзя редактировать/удалять;
операторское CLI-исключение описано выше.

### Паспорт машины и наблюдения

Устойчивые характеристики храните в `metadata.passport`, а состояние на момент проверки — в
`metadata.facts`. Паспорт не означает, что машина сейчас исправна. У каждого блока есть `source`
и `checked_at`; дата проверки без часового пояса не принимается, `null` сохраняет неизвестность.
Старая карточка без паспорта читается без автоматического извлечения характеристик из заметок.

| Поля паспорта | Значение |
| --- | --- |
| `hostname`, `os`, `kernel` | Имя машины, ОС с версией, версия ядра |
| `cpu_model`, `cpu_cores` | Модель CPU, количество доступных ОС логических CPU / vCPU (1–65536) |
| `memory_mib`, `swap_mib` | Общая RAM и swap в МиБ; 1 ГиБ = 1024 МиБ. Swap 0 означает отсутствие |
| `storage` | До 16 строк: устройство/том, ёмкость с единицами, тип и точка монтирования |
| `provider`, `location`, `virtualization` | Провайдер, локация/ЦОД, тип машины или виртуализации |
| `source`, `checked_at` | Непустой источник (по умолчанию `operator`) и дата проверки ISO либо `null` |

Текстовые поля и строки дисков ограничены 256 UTF-8 bytes. Числа памяти — целые до 2^40 МиБ;
RAM должна быть положительной, swap может быть нулевым. Пропущенное или `null` числовое поле
означает неизвестное значение. Весь паспорт входит в существующий лимит базовых полей 32 KiB.

В кратком и полном паспорте диски показаны отдельной таблицей: устройство/том, ёмкость,
тип и размещение. Для отдельных колонок разделяйте поля `;` или `·`, например
`/dev/vda; 64424509440 bytes; virtual disk; mount=/`.
Этот же формат опубликован в скилле и описании server_save. Прежний формат
`/dev/vda: 64424509440 bytes (60.000 GiB); disk; mount=нет` также раскладывается
по колонкам; исходная строка остаётся неизменной.
Целые объёмы в байтах отображаются в КиБ/МиБ/ГиБ/ТиБ; точное исходное значение доступно
при наведении. Произвольные строки остаются читаемыми целиком. Это только отображение:
исходные записи и дата проверки сохраняются, свободное место из ёмкости не вычисляется.

Patch без `passport` сохраняет его. Переданный `passport` заменяет весь блок: сохраняйте известные
поля при согласовании, не объявляйте старые непроверенные значения проверенными новой датой.
Если сведения блока не проверены вместе, оставляйте `checked_at: null`.
Свободная память, load average, заполнение файловой системы и сбои служб относятся к наблюдениям.
У факта по-прежнему обязательны `text`, `source`, `checked_at`; дополнительная `category` принимает
`system`, `hardware`, `resources`, `services`, `access`, `network`, `limitations` или `notes`.
Старые факты без категории сохраняют исходный формат. История аудитов и операций остаётся
отдельным журналом на вкладке «История».

До выполнения агент явно разделяет действия по цели. При смешанной работе кратко обозначает
части «Код» и «Сервер», прежде чем приступать к ним:

| Работа | Где хранить результат |
| --- | --- |
| Диагностика кода, SQL/GraphQL, бизнесовых данных, прикладные DML/миграции схемы, локальные тесты | Только Task проекта, в том числе при доступе через SSH/Docker |
| Фактическое изменение ОС, конфигурации, proxy/TLS/доступа, каталогов площадки, runtime/артефактов деплоя, портов/служб/контейнеров, перезапуск или обслуживание движка БД | `operation` сервера: что действительно изменено, когда и как проверено |
| Явно запрошенный аудит инфраструктуры сервера | `audit` сервера: инфраструктурные выводы, ограничения проверки и явное отсутствие изменений при read-only работе |
| Подготовка test/prod площадки | Фактическая инфраструктурная операция в истории плюс проверенные параметры сайта/профиля |
| Создание/правка/архивирование/импорт карточки реестра | Автоматическая история метаданных; отдельной удалённой операции не было |

При смешанной задаче проектная часть остаётся в той же Task, а в серверное событие входит только
инфраструктурная часть. Дополнительную Task ради серверной истории создавать не нужно.
Сам доступ по SSH, просмотр контейнера или проверка hostname не превращают проектное исследование
в серверный аудит. Реестр можно прочитать для подключения, но бизнесовые диагностики не переносятся
ни в историю, ни в `facts`/`sites`. Если цель неоднозначна, агент уточняет границу до выполнения
и записи. Работа без проекта не требует регистрации Workspace/Task ради истории сервера.
Профиль подготовки задаёт параметры, но не разрешает изменение production.

При конфликте записи в Dashboard нажмите «Обновить»: отредактированные поля сохранятся,
нетронутые поля получат актуальные значения, а повторная запись использует новую ревизию.
Перед сохранением проверьте согласованную карточку.
Ответ другой формы, включая конфликт, сохраняет исходную ревизию каждого соседнего черновика.
Только подтверждённая собственная запись обновляет свою ревизию; явное «Обновить» перечитывает
карточку для согласования. После удаления последней строки страницы Dashboard возвращает
существующую предыдущую страницу с сохранением поиска и положения профилей.

Хранимая карточка ограничена 512 KiB ASCII JSON, базовые поля — 32 KiB, отдельный сайт/профиль —
6 KiB, событие — 2400 bytes. Ответ домена — 48 KiB (MCP wrapper максимум 52 KiB), публичный
Servers request — 64 KiB. Только административный локальный IPC `import`/`enrich` допускает
1 MiB; остальные Servers IPC сохраняют 64 KiB, проектные контракты — 16 KiB.
`metadata.sites`/`platform_profiles` в ответе — ограниченные страницы. `site_id`/`profile_id`
выбирают точную запись; `sites_query` фильтрует имя, ID, назначение и домен. Параметры
`sites_offset`/`sites_limit` (по умолчанию5, максимум10), `profiles_offset`/`profiles_limit`
(по умолчанию4, максимум8) задают страницы; limit0 исключает ненужную коллекцию.
`sites_page`/`profiles_page` содержат `total` после фильтра/выбора, `full_total` всей коллекции,
`offset`, `truncated` и `next_offset`. Для полного перечня проходите `next_offset`, передавая
`expected_revision` из первой страницы; конфликт чтения требует начать проход заново. Страницы
и история могут уменьшиться по байтам, сохраняя хотя бы одну запрошенную запись и курсор прогресса.
Не записывайте страницу обратно как полный список; результат записи тоже постраничный.
Крупные отчёты разделяйте на полезные ограниченные записи, исключив секреты и сырые env/dumps.

Аудит разрешает только чтение. Skill требует проверки hostname/адреса/сервиса перед разрешённой
мутацией, сохранения границ совместных сервисов и текущей проверенной процедуры дампа перед
работой, способной затронуть БД. Установка мониторинга, изменение cron/config/service и отправка
уведомлений требуют прямого запроса. MCP только хранит результаты и ничего не запускает на хостах.

Официальные host-контракты проверены 2026-10-05:
[Codex MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli),
[локальные skills](https://learn.chatgpt.com/docs/build-skills).
Синтетическая проверка не заменяет подтверждение discovery/вызова модели в новом реальном чате.

## Сайты, приложения и подготовка площадок

В карточке сервера раздел «Сайты и приложения» хранит реальные экземпляры: постоянный `site_id`,
название/назначение, домены, окружение, стек с известными версиями, службы и способ запуска,
порты, пути, политика доступа без секретов, зависимости (включая несекретную ссылку на БД), источник и `checked_at`.
В версиях пустая строка означает неизвестность. `checked_at: null` не означает свежий аудит.
Карточка без приложений не доказывает отсутствие сайтов. Через формы можно добавлять,
редактировать и удалять записи; это не меняет файлы или сервисы на удалённом сервере.

Отдельный раздел «Правила подготовки площадок» хранит повторно используемые `platform_profiles`:
`profile_id`, название, окружение и стек, `domain_pattern`, `path_pattern`, `runtime`,
`access_policy`, краткие упорядоченные `steps`, зависимости, источник и время проверки.
Это правила подготовки, а фактические параметры уже подготовленной площадки находятся в `sites`.
Неизвестные шаблоны остаются пустыми: точный путь существующего приложения не доказывает шаблон.
У сайта `profile_id` может ссылаться на существующий профиль этой же карточки; пустая ссылка
означает неизвестное происхождение подготовки. Используемый профиль нельзя удалить, пока
связанные сайты не согласованы. Прежняя модель v28 ограничивала набор 256 приложениями; v30 выносит приложения в карту
с квотой 10 000 объектов разных типов. Профилей до 32; legacy-списков до 16 элементов, шагов
профиля до 12. Dashboard показывает все приложения либо выбранные страницы, а `server_save`
изменяет одну запись с CAS. Несохранённая POST-форма
вызывает предупреждение браузера при переходе. Подтверждённое удаление очищает только свой
редактор; чужие черновики, а также черновики при конфликте/неподтверждённой отправке сохраняются.

После разрешённой подготовки агент сохраняет фактические домены, пути, окружение, стек/версии,
запуск/порты, доступ и зависимости выбранного сайта, ссылку на профиль и свидетельство проверки.
Профиль не даёт разрешения менять сервер и не является исполняемым скриптом. Секреты, env,
сырые команды и дампы здесь не хранятся. После аудита сохраняются проверенные связи
домен → приложение → служба/путь/БД; непроверенные сведения не объявляются подтверждёнными.

## Контролируемый перенос связей из выбранной карточки

Свободный текст исходной карточки не позволяет универсально вывести принадлежность каждого
домена приложению. Для явно проверенного отображения используется отдельный JSON manifest:

```sh
harness servers import /path/to/server-monitoring --server source-id --sites-manifest /path/to/source-id.json
harness servers import /path/to/server-monitoring --server source-id --sites-manifest /path/to/source-id.json --apply --expected-revision 1
```

Manifest содержит ровно `source_id`, `card_sha256`, `index_sha256`, `sites`,
`platform_profiles`, `omissions` и optional `references` (до4 `{path,sha256}`). SHA-256
закрепляют прочитанные исходники. References разрешены только для явно связанных выбранной
карточкой regular Markdown внутри исходного корня, с проверенным хешем и размером до128 KiB.
Сам manifest — до512 KiB; symlink, выход за корень и произвольные файлы запрещены. Каждый сайт имеет
ссылку `server-monitoring/.cursor/rules/host-source-id.mdc#L10-L20`; профиль может ссылаться на
эту карточку или индекс с таким же line anchor. Допускается anchor явно закреплённого references
файла; несколько anchors разделяются `;`. Все импортированные `checked_at` остаются null.
`omissions` — до 8 коротких несекретных описаний пробелов; они сохраняются как непроверенные
факты, доступные пользователю и агентам без папки. Manifest не содержит сырых исходников или
секретов; его содержание следует проверить по одной выбранной карточке перед применением.

Импорт добавляет лишь новые IDs сайтов/профилей и ссылки/факты. Он сохраняет поля оператора,
изменённые экземпляры и профили; сохраняется и удаление ранее импортированного ID. Это обеспечено
daemon-owned ledger, а не только сравниванием текущего списка. CAS конфликт ничего не добавляет.
Обычный `server_save` изменяет базовые поля или одну child-запись, не заменяя соседние сайты/профили. Исходный server-monitoring остаётся неизменным.

## Отсутствие следов исполнителя

Общее правило skill действует при аудите и разрешённом обслуживании, включая подготовку
площадок: названия файлов/config/cron/env и комментарии описывают рабочую задачу, без подписей
Cursor/Codex/AI/агента. Не создавайте README, датированные .bak, оставленные скрипты или
временные файлы ради отчёта о работе. Нужные для задачи резервные копии и эксплуатационные
комментарии допустимы. Логи содержат штатный вывод сервиса; формат мониторинга сохраняется.
Уведомления об установке/настройке и тестовые алерты требуют прямого запроса. Правило не
разрешает удалять существующие логи, скрывать изменения или подавлять штатный audit trail.
После изменения проверяйте результат и убирайте только собственные лишние артефакты;
подтверждённый контекст сохраняйте в существующей карточке.

## Связанная карта сервера (schema v30)

Новая карточка состоит из обзора, приложений, доменов и маршрутов, каталогов, служб и сертификатов.
Прежние заметки, паспорт, подготовка и история сохранены. По умолчанию список показывает **все**
известные записи; можно выбрать 25/50/100, искать и сортировать весь набор до разбиения на страницы.
Числа «всего», «совпадений» и «показано» различаются. Карточка отдельного объекта открывается по
постоянной ссылке, показывает основания и связи и содержит один редактор. Связанные списки
приложения фильтруются отдельно. Просмотр экрана не запускает аудит.

Открытие записи и возврат к списку сохраняют поиск, сортировку, размер страницы и позицию.
Один шаг Back возвращает из связанного списка к прежней карточке. «Отменить изменения»
сбрасывает только выбранную форму; соседние черновики сохраняются. Ошибка сохранения
показывается с понятным действием и переводит фокус к сообщению, сохраняя введённые значения.
При ошибке входящей или исходящей связи остаётся выбранная карточка одного из её объектов;
черновик относится только к отклонённой форме. Краткий паспорт перед списком приложений
показывает дату, источник и давность по тому же интервалу, что полный паспорт. Ссылка ведёт
к полному паспорту и источнику; неизвестная дата и незаполненный паспорт указаны явно.

В обзоре характеристики сгруппированы по назначению и системе, оборудованию и размещению.
Полный паспорт раскрывается отдельно; переход к источнику или редактору раскрывает его
автоматически. Обзор показывает первые шесть приложений и ссылку на полный список, а счётчики
объектов ведут в соответствующие коллекции. Проблемы и невыясненные сведения вынесены в отдельные
блоки; на узком экране они идут перед списком приложений. Охват проверок и правила давности
раскрываются по запросу.

Публичных MCP tools по-прежнему пять. Для нового клиента сначала прочитайте
`server_get(server_id, collection="schema")`: ответ содержит точные типы полей, допустимые состояния,
операции и правила. Коллекции: `application`, `domain`, `route`, `directory`, `service`, `certificate`,
`certificate_version`, `certificate_use`, а также `checks`. Пример чтения:

```json
{"server_id":"chosen-id","collection":"application","query":"example.test","sort":"name","limit":100,"offset":0}
```

`query` ищет обычный записанный текст, включая кавычки и обратные слеши, и также ищет по явно
связанным доменам, путям и службам. `status` принимает состояния выбранной
коллекции либо `unknown`/`stale`/`attention`; `application_id` выбирает непосредственные связи
приложения. `sort`: name/status/environment/size_bytes/not_after/checked_at; `descending`: boolean.
Ответ содержит revision, total, matched, rows, next_offset, complete. Для полного чтения повторяйте
next_offset с исходной expected_revision до complete; конфликт требует перечитать весь набор.
`object_id` выбирает подробности и связи с links_total/links_offset/links_next_offset.

`server_save(..., map_operation=...)` выполняет одну операцию. Объект:

```json
{"action":"upsert","kind":"application","object_id":"shop","data":{"name":"Магазин","purpose":"Витрина","source":"operator","usage":"active","availability":"unknown"}}
```

Это полная выбранная запись: сохраняйте её прежние поля и evidence. Другие объекты и связи не
заменяются. `delete` требует kind/object_id и отсутствия связей. `link` принимает link с link_id,
from_kind/from_id/to_kind/to_id, role, source, checked_at, basis, reason; `unlink` — link_id.
Все endpoints относятся к выбранному серверу и проверяются FK. Бизнес-контекст проекта и ссылки
на внешнее размещение можно явно описать в несекретных dependencies/description; такие ссылки
не расширяют права и не становятся автоматически проверенными отношениями другого сервера.

Домены имеют отдельные discovery_sources, DNS и результаты публичной/origin проверки; отдельные
route records сохраняют адрес, имя, порт, путь и время каждого проверенного места. Шаблон имени
не считается работающим доменом. Каталоги показывают контекст, роль, наличие, размер и способ
измерения. Возраст не означает мусор. Для leftover обязательны basis=operator, причина, прежнее
закрытое приложение, decision_owner, decision_at и links_checked_at; текущая связь активного
приложения запрещает эту классификацию. Для retained требуется retention. Candidate остаётся
кандидатом, unknown — неизвестным; реестр не удаляет файлы.

Сертификат управления хранит выпуск, продление, применение, ответственного и ручную процедуру.
Версия хранит публичный fingerprint, issuer, SAN и срок. Использование хранит file/config/key
references без содержимого ключа, configured/file/observed fingerprints, адрес, SNI, порт и
observed_at. Совпадение файла и ответа не предполагается. current_version связывает действующую
наблюдавшуюся версию с управлением и определяет отображаемый срок; new_version хранит ещё не
применённый выпуск. verified для renewal_state/deployment_state требует dated probe evidence
именно этого поля: наличие certbot/timer подтверждает только configured.

Проверки сохраняются порциями, без стирания непроверенного:

1. check_start: check_id, coverage (area/state/source/reason), source, started_at.
2. check_append: check_id, batch (с нуля), observations (1..25 записей kind/object_id/values/source/
   checked_at/basis/reason). Сохраняйте возвращённую revision после каждой порции.
3. check_publish: check_id, coverage, finished_at. Порции должны быть последовательными; публикация
   атомарна. check_fail с check_id/reason сохраняет неудачное завершение.

Охват принимает complete/partial/failed/not_checked для каждого типа. Наблюдения допускаются только
в complete/partial областях, не меняют операторское назначение, название уже существующего объекта,
использование, ответственного и процедуру. Более старый отчёт не заменяет новое field evidence.
Отсутствие записи в порции ничего не удаляет. Черновик виден в охвате проверок, но не в текущих
состояниях объектов. Все реальные записи черновика повышают server revision; повтор той же порции
с тем же содержимым идемпотентен, другой payload под тем же номером отклоняется. При сторонней
правке черновик конфликтует: автоматического повышения его expected_revision нет.

Политика map_policy задаёт health_hours/inventory_hours/passport_days и expiry_days; по умолчанию
24 часа/168 часов/30 дней и предупреждения 30/14/7 дней. Даты отдельных операционных полей влияют
на давность; новое описание не освежает старую проверку HTTPS. Политика редактируется в обзоре.

Миграция v30 сохраняет точные bytes исходной карточки в server_legacy_snapshots, прежние IDs,
паспорт, историю, профиль, импортные ledgers и операторские поля. Явные старые домены/пути/службы
переносятся как reference, с неизвестной актуальностью; свободные заметки не анализируются.
Текущие объекты принадлежат нормализованным таблицам. Старый site API остаётся ограниченной
проекцией для совместимости и меняет только прежние поля.
Совместимые записи добавляют в карту только новые явно внесённые домены, пути и службы.
Правка назначения сервера, профиля или описания приложения не восстанавливает удалённые
объекты и связи из неизменённых старых списков.

Квоты: 10 000 объектов и 20 000 связей на сервер; 12 KiB ASCII JSON на объект (legacy-поля
приложения сохраняют 6 KiB/16 элементов); 64 элемента обычного списка, 32 field evidence;
1 000 проверок, 400 порций на проверку. Квоты отклоняют запись явно. MCP-выдача сохраняет
48/52 KiB, запрос — 64 KiB; продолжение учитывает фактическое сокращение по байтам. Черновики
не удаляются автоматически. Миграция сохраняет прежние наборы даже сверх новой квоты;
добавление сверх квоты отклоняется, чтение полного старого набора остаётся доступным. Доступ к проекту, vault и удалённому исполнению не добавлен.

Эта реализация проверяется на отдельной синтетической БД. Установка обновления и повторный аудит
реальных серверов, включая blue-ant, выполняются отдельно по явному запросу.

### Понимание размещения и границы проверки (schema v31)

Чтение коллекций не меняет данные. `status`/сортировка состояния используют известный технический
результат: `usage=unknown` больше не скрывает running/failed службы или доступность адреса.
Ответ выбранного объекта содержит `understanding`, а компактные строки — observed_status,
technical_usage, observed_reason, effective_availability, entry_type_effective, effective_role.
Наблюдаемое техническое использование отделено от операторского usage:

- `current`: свежая configuration/process связь с запущенным/запланированным потребителем;
- `configured`: связь конфигурации есть, текущий запуск не подтверждён;
- `unknown`: актуальное потребление не доказано. Частичная проверка не доказывает ненужность.

У приложения текущий запуск подтверждается явно связанной runtime-службой. У пути current
приоритетно показывает текущих потребителей, сохраняя решение оператора. Противоречие прежнего
leftover показано отдельно; новое leftover с текущим потребителем отклоняется. Retained/leftover
по-прежнему требуют своих операторских оснований. Никакое состояние не удаляет файлы.
Новые положительные связи и публикация технических наблюдений сохраняются даже при старом
решении leftover: они позволяют показать его противоречие. Наблюдение размера/типа не подтверждает
решение оператора повторно. Явный upsert с leftover означает новое или повторное решение и
проверяет текущих потребителей в той же транзакции.

`understanding.related` содержит application/domain/route/service/directory: total и до шести
коротких items (object_id/name/role/verified). Это краткий обзор, полный перечень — прежние
links_total/links_next_offset. Dashboard показывает переходы между доменами, маршрутами,
запуском/зависимостями и каталогами; отсутствие назначения/проверки остаётся явным вопросом.
Общий ASCII JSON бюджет related — 8 KiB; omitted сообщает число не показанных ссылок каждого
типа, total остаётся полным. Полные связи читаются по независимому курсору без потери записей.
Фильтры current/configured учитывают technical_usage; приложение с проверенным runtime также
доступно по running. Операторский active/closed остаётся отдельным условием отбора.

Новые наблюдаемые поля пути:

| Поле | Значения |
| --- | --- |
| `entry_type` | unknown/directory/file/socket/symlink/other; определять по файловой системе, не имени |
| `consumer_checks` | список полностью проверенных для этого пути источников docker/systemd/cron/proxy/symlinks |

Размер size_bytes остаётся null до измерения; size_method описывает метод. Проверка одной Docker
связи не означает полный поиск Docker потребителей. Consumer checks требуют своей свежей даты и
проверенного основания; новые поля не освежают старые. Dashboard фильтрует полный набор по типу
пути и техническому состоянию. Заголовок «Каталоги и технические пути» включает прежние файловые
ссылки; они сохраняются и явно отделяются от подтверждённых каталогов.

Application/domain/route имеют `probe_scope=unknown|transport|endpoint|functional`, `probe_url`
и `expected_result`. При endpoint/functional URL и ожидаемый ответ обязательны. Для поискового
GET / используйте transport; API HTTP403/404 там отображается как «Работа приложения не проверена»,
с исходным результатом. DNS/TLS/5xx и ошибка проверенного ожидаемого endpoint остаются ошибками.
Успешный HTTP200 на корне сам по себе не означает проверку всей функциональности. Датированные
scope и public_result должны совпадать с проверкой доступности по источнику, дате и основанию probe;
одинаковое время разных источников не подтверждает общий охват. Старый scope не меняет
смысл более нового результата. `understanding.gaps` перечисляет недостающий охват и вопросы.
Прежний маршрут GET / может использовать явно связанное объяснение корня API от домена:
проверенные связи, совпадающие имя/код ответа и источник, свежие даты availability/public_result
одной серии с разницей не более минуты. Прежний process-вывод приложения с GET / и проверенным
runtime использует такие связанные домены/маршруты. Более новая общая дата записи не заменяет
дату поля availability. Непроверенные/устаревшие связи, несовместимые проверки и настоящие ошибки
связанного endpoint не превращаются в успех. Явные собственные HTTP5xx/curl/TLS/DNS ошибки
приложения имеют приоритет перед соседним транспортным ответом корня. Исходные данные при чтении
не меняются. Если текущий вывод отличается от сохранённой оценки, карточка показывает их отдельно,
с источником и датой поля прежней оценки; обычная подтверждённая ошибка остаётся текущей ошибкой.
Свежая собственная `origin_result` с probe-доказательством имеет приоритет над root403/404:
внутренняя HTTP/curl/TLS/DNS ошибка остаётся видимой. Origin и public могут быть независимыми
проверками с разными источниками/датами; происхождение и свежесть подтверждаются для каждого
поля отдельно. Более новая общая дата с доказательствами других полей не проверяет origin.
Связанная внутренняя ошибка в выводе маршрута/приложения отмечается как сбой связанной точки,
с её источником и датой. Собственный публичный ответ показан отдельно; внутреннее предупреждение
не означает ошибку внешнего запроса, использование этого TLS прокси или проверку функции API.
Длинные результаты/источники сокращаются в объяснении; полные исходные поля сохраняются.

Публикуйте эти наблюдения обычными check_start/append/publish; usage/purpose/description и решения
о хранении остаются операторскими. Скилл server-operations задаёт последовательность bounded
инвентаризации текущих размещений и соседних старых корней. Миграция v31 не переписывает данные;
старые writers/validators v30 отказывают, чтобы не потерять новые типизированные поля.
