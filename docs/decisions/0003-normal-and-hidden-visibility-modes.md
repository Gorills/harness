# ADR-0003: Normal and Hidden project visibility modes

- **Status:** Accepted
- **Date:** 2026-08-21
- **Deciders:** Repository architecture baseline

## Context

Harness materializes host-native project artifacts such as skills and rules even though the canonical registry and durable state live outside repositories. The original specification already says generated project skills should not normally enter commits and prefers `.git/info/exclude` over editing `.gitignore`.

A stronger product requirement adds two explicit operating modes:

- **Normal**: normal native-agent/Git behavior is allowed, including durable SCM actions when the user/host permits them.
- **Hidden**: Harness integration must not leave agent-identifying repository/history artifacts, and Harness-owned project projections must remain local-only without modifying tracked ignore/instruction files.

Git ignore rules alone cannot provide the stronger guarantee. `$GIT_COMMON_DIR/info/exclude` is intentionally repository-local and untracked, but `git add -f` can bypass ignores. In linked-worktree repositories the `info` directory belongs to the common Git directory, so the exclude list is shared by all worktrees. Git also explicitly warns that `assume-unchanged` and `skip-worktree` are not general mechanisms for ignoring changes to tracked files.

Native hosts also differ in how much policy can be enforced. Some provide local project settings, sandbox/permission controls, and attribution settings; others expose only prompt-level rules or inject attribution outside the local Git process. Harness does not own an agent runtime, so it cannot honestly claim a cross-host restriction that the selected host cannot enforce.

## Decision

### 1. Mode is durable Project policy

Persist `visibility_mode = normal | hidden` as Project policy in `harnessd`. New Projects default to `normal`. `project_status` exposes only the effective mode to the model; host capability/enforcement diagnostics remain operator-facing. Mode changes are explicit human/operator actions through non-model-facing surfaces; no v1 MCP tool can switch a Project into or out of Hidden mode. Entering Hidden performs repository/projection preflight before the policy becomes effective; every later agent/bridge admission independently validates the resolved host profile before Harness serves Hidden project context.

In v1, all Harness Workspaces that resolve to the same Git common directory MUST use the same effective visibility mode. `$GIT_COMMON_DIR/info/exclude` is shared across linked worktrees, so allowing contradictory per-worktree modes would make Git visibility non-local and surprising.

A future per-worktree override requires an independently verified isolation mechanism and migration/acceptance coverage; it is not part of v1.

### 2. Normal mode

Normal mode preserves ordinary native-host behavior:

- agents may perform SCM mutations when the host/user permissions allow them;
- host-native commit/PR attribution is not suppressed by Harness unless the user configured it separately;
- generated Harness project artifacts remain local-only by default, consistent with the original specification, but the user may explicitly export/share selected generated material later through a separate product operation.

Harness still never silently edits `.gitignore` merely to support its own generated files.

### 3. Hidden mode is repository/SCM invisibility, not provider invisibility

Hidden mode covers durable repository and SCM surfaces. It does **not** promise to hide AI usage from provider-side telemetry, enterprise analytics, local application databases, network logs, or other systems outside the repository/SCM contract.

Within the supported Harness integration, Hidden mode requires all of the following:

1. Agents may read Git state/history but MUST NOT perform durable SCM mutations. This includes staging/index writes, commit/amend, branch/ref creation or rename, tags, push/force-push, PR creation/editing, issue creation/editing, reviews, SCM comments, releases, or equivalent provider/MCP mutations.
2. Humans remain free to perform those operations outside the agent execution path. Harness does not rewrite the user's Git identity to an agent identity.
3. Agent-authored source/docs may contain normal technical comments and documentation, but MUST NOT add self-identifying meta text such as "generated by", `Co-Authored-By`/`Made-with` agent trailers, vendor/model signatures, agent-specific branch prefixes, or PR/issue footers solely to advertise agent involvement.
4. Harness-owned project artifacts required by a host (skills, rules, local settings, manifests, compatibility shims) MUST remain untracked and Git-ignored without changing `.gitignore` or any tracked instruction/config file.
5. If a host profile cannot enforce the required SCM-write restriction or requires a tracked/user-owned file to inject the Hidden policy, that host/profile is **unsupported for Hidden mode**. Harness fails closed for that admission and must not silently downgrade the Project to Normal or report Hidden as enforced for that session.
6. This guarantee applies to agent sessions admitted through the Harness integration. Harness cannot prevent an unrelated agent/tool that the user launches outside Harness from mutating the same repository, and it does not claim to do so.

Prompt instructions are defense-in-depth, not the enforcement boundary for rule 1.

### 4. Hidden projection uses Git-local excludes

Canonical Harness artifacts stay outside repositories under Harness-owned state/registry paths. Only host-required projections are materialized into the working tree.

For every Hidden projection plan, the adapter/application layer MUST:

1. resolve the repository-local exclude path through `git rev-parse --git-path info/exclude` rather than assuming `.git` is a directory; when repository identity is needed, resolve the common directory through Git as well;
2. reject any target that is already tracked, collides with an unknown user-owned path, or escapes the Workspace through a symlink/indirection;
3. parse before write, add only exact root-anchored Harness-owned patterns inside an identifiable managed block, preserve every non-Harness byte exactly, and replace atomically; back up a pre-existing non-empty user exclude file before the first Harness rewrite;
4. materialize only Harness-owned files selected by the projection plan;
5. verify the projected paths are untracked and ignored;
6. verify the repository `.gitignore` content did not change;
7. on cleanup, remove only Harness-owned projected files and Harness-owned exclude entries and preserve the remaining user file exactly.

Do not use `assume-unchanged` or `skip-worktree` for Hidden artifacts. They operate on tracked index entries and are not a supported local-ignore mechanism.

### 5. Ignore is not a security boundary

Hidden-mode correctness MUST NOT be justified by `.git/info/exclude` alone. Standard Git intentionally allows forced staging of ignored files.

The hard boundary for agent-originated history pollution is the host-specific SCM-write denial. Git hooks may additionally reject staged Harness-owned paths or normalize messages, but they remain defense-in-depth because client hooks/config can be bypassed or replaced and linked worktrees share common hook/config surfaces.

### 6. Host capabilities are explicit

`HostAdapter` exposes normalized Hidden-mode capabilities rather than leaking host names into core policy. Admission uses a Harness-owned installed adapter/profile record (for example, adapter-managed MCP registration/bridge metadata), never self-reported MCP `clientInfo`. At minimum the adapter profile must report:

- `local_hidden_instructions`: can inject an untracked, project-local always-on rule without replacing tracked user instructions;
- `scm_write_enforcement`: can deny agent-originated local and remote SCM mutations strongly enough for the supported execution profile;
- `policy_integrity`: the agent cannot rewrite, disable, bypass, or escalate around the effective Hidden enforcement during the supported session/profile;
- `attribution_suppression`: can disable host-injected durable attribution where that host can still create such artifacts outside ordinary Git commands;
- `hidden_projection_paths`: project-local host paths that can be safely materialized and excluded;
- `verification_method`: deterministic doctor/acceptance evidence for the above.

Hidden admission succeeds only when every required capability for the resolved host/profile is verified. Unsupported/unverifiable profiles receive a bounded actionable error and do not receive normal Hidden project context. Unknown is not equivalent to supported.

### 7. Current host evidence

Current documentation provides useful building blocks but not a universal guarantee:

- **Claude Code** documents local project settings (`.claude/settings.local.json`), project/local instruction surfaces, fine-grained Bash permissions, OS-level sandbox filesystem restrictions, and explicit commit/PR attribution settings that can be empty. This makes the local Claude profile a strong candidate for enforceable Hidden support, subject to real-host acceptance and ensuring bypass/unsandboxed escape paths are disabled for that profile.
- **Cursor IDE/CLI** documents project rules and a user/admin attribution control, but the safe machine-readable per-project enforcement surface for all SCM writes is not established by the docs reviewed here. Hidden remains acceptance-gated. Cursor Cloud/background-agent behavior is a separate profile: official docs reviewed here do not establish a complete cloud attribution-suppression contract, and current Cursor staff support separately reports cloud `Co-authored-by: Cursor` behavior as independent of the local attribution setting. Cloud therefore must not inherit local Cursor Hidden support automatically.
- **Antigravity** documents workspace rules under `.agents/rules` and a deny/ask/allow permission engine with project-scoped settings in the IDE. This is a candidate enforcement surface, but local/CLI/IDE profiles require separate acceptance because their configuration scopes differ.
- **Codex** has project instruction discovery and a local override filename, but prompt instructions are not an SCM enforcement boundary and `AGENTS.override.md` can replace same-directory base instructions. Current Codex source also contains managed permission profiles that can make project roots writable while denying a `.git` subpath (covered at least by Windows sandbox tests), which is a promising enforcement primitive rather than proof of end-to-end Hidden support. Hidden therefore remains acceptance-gated until the adapter proves policy injection/integrity, cross-platform local Git denial, remote-SCM denial, and restoration without shadowing tracked `AGENTS.md`.

No host is marked production-supported for Hidden solely from documentation review. The real-host acceptance matrix is the release gate.

## Consequences

### Positive

- `.gitignore` stays untouched by Hidden installation, and operator-only mode switching prevents the agent from simply disabling the policy through Harness.
- Generated Harness agent artifacts stay out of normal Git status/add flows.
- Hidden semantics are honest about what can and cannot be enforced without owning the agent runtime.
- Worktree sharing behavior is explicit instead of producing cross-checkout surprises.
- Hosts that inject unavoidable attribution fail closed rather than silently violating the mode.

### Costs

- Hidden mode is intentionally more restrictive: the human owns staging/commit/push/PR/review publication.
- Hidden support is profile-specific and may initially be unavailable for some hosts.
- Adapters need additional local-settings/permission handling and acceptance coverage.
- `.git/info/exclude` mutation needs ownership markers, backup/atomic-write discipline, and worktree-aware tests.

## Verification

Core/integration tests must cover:

- `normal` default plus `normal`/`hidden` Project policy persistence, with no model-facing mode mutation path;
- `project_status` schema exposes only the effective `visibility_mode` enum and does not leak host enforcement/configuration internals;
- Hidden admission rejects an unsupported/unverifiable host profile without downgrading Project policy, and never uses self-reported `clientInfo` as enforcement identity;
- rejection of contradictory modes for Workspaces sharing one Git common directory;
- Hidden projection into an ordinary repository with `.gitignore` byte-for-byte unchanged;
- Hidden projection into a linked worktree and proof that the common exclude file is shared;
- tracked-path and unknown-user-file collisions fail before overwrite;
- every Harness-owned Hidden projection path is absent from `git ls-files --cached`, absent from normal `git status --porcelain --untracked-files=all`, and reported ignored by Git;
- exclude updates preserve every unrelated byte, use atomic replacement/backup discipline, and cleanup removes only Harness-owned entries/files;
- a forced-add test demonstrates why ignore alone is insufficient and therefore must not be used as the enforcement proof;
- no use of `assume-unchanged`/`skip-worktree` for projection hiding.

Real-host acceptance for each supported Hidden profile must additionally prove:

- Hidden instructions/settings are actually loaded and the agent cannot modify, disable, or bypass their enforcement;
- a supported Harness-owned profile identity is required for admission, while spoofed/self-reported client metadata cannot grant Hidden support;
- agent attempts to stage, commit, create/rename refs, tag, push, create/edit PRs/issues/reviews/comments, or equivalent remote SCM mutations are denied rather than merely discouraged;
- ordinary source/test edits still work;
- no host/vendor/model attribution is injected into durable Git/SCM artifacts;
- Harness-owned project rules/skills/settings remain untracked and `.gitignore` remains unchanged;
- switching back to Normal removes only Harness-owned Hidden policy/projection state and restores the prior host configuration exactly.
