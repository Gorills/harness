# ADR 0081 Связанная карта сервера и проверяемая инвентаризация

- Статус: кандидат реализован в checkout; ожидает независимой проверки и рассмотрения оператором
- Дата: 2026-10-06
- Область: развитие модели Servers из ADR 0080
- Пользовательское описание: [Карта сервера и приложений](../server-map-design.md)

## Основание решения

Человеку нужна понятная актуальная картина размещения. Набор свободных заметок и вложенных
списков в карточке не позволяет получить полный сортируемый перечень доменов, отличить
используемые каталоги от остатков старых сайтов или понять механизм обновления сертификата.
Пятистрочная страница полных сайтов также слишком мала для человеческого обзора.

Предлагается сохранить daemon-owned Servers и существующие границы доступа, добавив
типизированные связанные записи и отдельные компактные представления списков.
Новая архитектура остаётся внутри текущего процесса и SQLite. Дополнительный сервис,
графовая БД, универсальный редактор графа и универсальная система выполнения команд не нужны.

## Владение данными и идентичность

Сервер остаётся корнем изменения и ревизии. Приложение обозначает размещение на этом сервере;
ключ существующего сайта server_id + site_id сохраняется. Деловое объединение нескольких
размещений в глобальное приложение можно добавить позже по явной связи, если возникнет
конкретная потребность. Имя сайта, домен и IP не являются доказательством идентичности сервера
или приложения и не используются для автоматического объединения.

Коллекции выносятся из большого JSON карточки в таблицы домена Servers. Паспорт, подключение
и небольшие общие поля остаются базовыми метаданными. Таблицы v30: server_map_objects, server_map_links, server_map_checks, server_map_batches
и server_legacy_snapshots. Точные поля доступны через server_get(collection="schema") и
описаны в [руководстве](../servers.md#связанная-карта-сервера-schema-v30).

| Сущность | Что хранит и с чем связана |
| --- | --- |
| Размещение приложения | Существующая идентичность сайта, название, назначение, окружение, операторское использование, ссылки на проект и другое размещение |
| Домен | Нормализованное DNS-имя либо явно отмеченный шаблон; все источники обнаружения; наблюдения DNS |
| Маршрут | Имя, протокол, порт и известное условие пути; конфигурация, приложение/перенаправление/прокси; проверяемый адрес |
| Каталог | Сервер, путь и известный контекст тома/контейнера; наблюдаемое существование, размер и способ измерения |
| Связь приложения с каталогом | Роль кода, загрузок, релиза, копии, данных; основание и время проверки |
| Экземпляр службы | systemd unit, контейнер, процесс или задание; способ запуска, состояние и роль |
| Связь службы | Потребители, обслуживаемые маршруты, используемые каталоги и общие зависимости |
| Управление сертификатом | Устойчивый контекст клиента/поставщика и места выпуска; способ продления, ответственный и процедура |
| Версия сертификата | Отпечаток публичного сертификата, issuer, срок, покрываемые имена; версия в контексте управления |
| Использование сертификата | Место обработки HTTPS, маршрут/служба, известные файловые ссылки, настройка применения, ожидаемая и наблюдаемая версии |
| Проверка и наблюдения | Охват, начало/конец, результат; типизированные значения, источники и времена; основания связей и классификаций |

Имена нормализуются последовательно с сохранением исходного написания для отображения.
Шаблоны не превращаются в реальные DNS-имена. Маршруты различают Host/SNI, порт и известный
путь; публичная проверка и прямой запрос к origin сохраняются раздельно. Ошибки разных A/AAAA
или узлов не сворачиваются в успешный результат одного адреса.

Путь не отождествляется с физическими данными: отдельно известны символическая ссылка,
цель, контейнерное отображение и общий том. Неизвестность этих связей сохраняется.
Роль каталога относится к связи с приложением. Общий каталог может иметь нескольких потребителей.

Отпечаток идентифицирует версию сертификата, а не политику продления. Одинаковая версия
может использоваться в нескольких местах; выдача новой версии не разрывает историю механизма.
Одно использование допускает несколько обслуживаемых версий, например RSA/ECDSA.
Неизвестная внешняя точка обработки HTTPS имеет отдельную ограниченную ссылку; запись её адреса
не разрешает исследовать внешнюю инфраструктуру. Связи внутри сервера проверяются FK;
внешнее размещение указывается явно в несекретном контексте приложения. Строгие FK-связи
в этой реализации ограничены выбранным сервером; внешняя ссылка не обходит другой сервер
и не выдаётся за проверенное отношение его объектов.

## Наблюдения и текущая картина

Операторский смысл и техническое наблюдение имеют разных владельцев. Автоматизированное
сопоставление не заменяет назначение, решение о закрытии, причину хранения или ответственного.
Для каждого операционного вывода требуется тип основания; свободный текст объяснения дополняет,
а не заменяет его. Классификации имеют проверяемые правила из пользовательского проектирования.

Текущая картина вычисляется из принятых наблюдений и операторских решений. Наблюдение
содержит время фактической проверки, время получения реестром, объект, тип значения,
источник и ссылку на проверку. Более поздняя загрузка старого отчёта не вытесняет новое
наблюдение. Противоречивые результаты разных точек проверки сохраняются с контекстом.
Успех последней попытки, последний успешный результат и давность различаются.

Охват проверки перечисляет области, источники и результаты каждой области. «Все найденные»
означает все записи известной инвентаризации с этим охватом. Полный отрицательный результат
может утверждать только отсутствие в проверенных источниках на определённое время.
Неполная проверка не является основанием удаления, прекращения использования или признания мусором.

Получение результатов поддерживает ограниченные порции в черновик одной проверки. Черновик
не выдаётся за завершённую карту. После проверки ссылок, типов и ожидаемой ревизии результаты
публикуются в одной SQLite-транзакции с изменением ревизии сервера и записью факта инвентаризации.
Допускается публикация явно частичного результата с сохранением прежних сведений непроверенных
областей. Ошибка и незавершённый черновик видны как состояние проверки.

Повтор порции различается по ID проверки и номеру порции; тот же номер с другим содержимым
отклоняется. После неизвестного исхода записи клиент сначала читает результат, а не повторяет
операцию вслепую. Публикация со stale revision не проходит. Клиент перечитывает изменившиеся
данные и согласует конфликт; автоматическое повышение ревизии черновика не допускается.
Квоты: 1 000 проверок на сервер, 400 порций по 1..25 наблюдений. Черновики не убираются
автоматически и остаются видимыми; срок хранения не вводится молча. Каждая реальная запись
черновика повышает server revision и собственную ожидаемую ревизию на один; сторонняя
правка вызывает конфликт, а не автоматическое согласование. Повтор той же порции не повышает ревизию.

## Чтение и изменение

Dashboard получает компактные строки списка и отдельно подробности выбранного объекта.
Режим «Все» получает полный компактный список в одном HTTP-ответе одного SQLite read snapshot;
это не MCP-ответ и не выдача подробных редакторов всех объектов. Страницы по 25/50/100
остаются альтернативным выбором пользователя; MCP проходит ограниченные страницы с CAS. При изменившейся ревизии нельзя смешивать страницы:
показанный список сохраняется с сообщением и предложением обновить набор.
Фильтрация и сортировка происходят до пагинации, с устойчивым вторичным порядком по ID.
Число совпадений и общий итог вычисляются по всему набору.

Страница содержит ревизию, итог, число совпадений, число выданных строк, продолжение и признак
завершённости. Байтовое сокращение страницы возвращает реальное продолжение, а не увеличивает
курсор на запрошенный размер. Подробности источников и отношения высокой кратности также читаются
страницами; у отдельной карточки всегда виден полный итог связей.

Пять публичных server tools сохраняются. server_get получает явный выбор коллекции/объекта,
фильтры и порядок; server_save — типизированную операцию над объектом или черновиком проверки.
Совместимый контракт описан в руководстве и collection="schema". server_record продолжает
отражать инфраструктурный аудит и реальные операции; CRUD реестра не превращается в удалённую работу.
Новая выдача ограничена существующими 48 KiB домена, 52 KiB MCP wrapper и 64 KiB публичного запроса.
Результат записи не содержит всю коллекцию. Полные списки проходят страницы; предел одной
карточки JSON и прежнее ограничение 256 сайтов не переносятся на нормализованную коллекцию.
Защитные квоты: 10 000 объектов/20 000 связей на сервер, 12 KiB на объект, 64 элемента
обычного списка, 32 field evidence. Старые application поля сохраняют 6 KiB/16 элементов.
Миграция сохраняет даже прежний набор сверх новой квоты; добавление сверх квоты отвергается
без обрезания, чтение прежнего полного набора остаётся доступным.

Все изменения проверяют server_id и expected_revision; одна операция транзакционно меняет
только заявленные записи/связи и сохраняет соседей, базовые поля и проектные ссылки.
Удаление записи с зависимостями не оставляет висячих ссылок. Архивирование сохраняет идентичность,
связи и историю. Пользовательское решение об остатках не выполняет удаление на сервере.
Черновики форм, конфликты, неопределённый исход записи и no-JS доступ сохраняют действующие гарантии.
Ошибка формы связи сохраняет карточку её выбранного endpoint в пределах текущего сервера,
независимо от направления связи. Поиск сравнивает введённый текст со значениями полей,
включая вложенные основания, без экранирования JSON. Краткий паспорт показывает дату,
источник и ту же оценку давности, что полный, с прямым переходом к полным основаниям.

## Границы исполнения и раскрытия

Daemon хранит карту и принимает структурированные результаты. Агенты выполняют согласованную
инвентаризацию через существующие средства исполнения; новый каталог не исполняет SSH,
обработчики продления, произвольные команды или чужую сохранённую процедуру.
Открытие карточки и обновление её экрана не запускают удалённую проверку.
Периодические проверки, уведомления и изменение серверов остаются отдельными явными действиями.

Сохраняются bearer authentication, loopback Host checks, bounded IPC/HTTP и разделение project MCP.
Серверные ссылки не расширяют права на проект, vault или соседний сервер. В инфраструктурный
реестр не переносятся результаты SQL, кодовая диагностика и бизнес-данные из проектного Task.

Файловые пути ключей допускаются как ссылки. Содержимое ключей, DNS API credentials,
ACME account keys, токены, пароли, сырые конфигурации и команды с секретами запрещены.
Источники принимаются как ограниченные типизированные несекретные ссылки и пояснения.
Текст конфигурации и импортированные документы не являются инструкциями для исполнителя.
Реальные ограниченные сообщения об ошибках не отражают запрещённый входной payload.

## Переход со старых карточек

1. Сначала разделить компактный список существующих сайтов и подробные записи. Это исправляет
   просмотр всех приложений без необходимости выдумывать новые домены и связи.
2. Расширяющая миграция создаёт таблицы и переносит существующие явно записанные сайты со стабильными
   ключами. Домены, пути и службы из прежних списков становятся документированными ссылками
   с прежним происхождением и неизвестной актуальностью, а не проверенными объектами использования.
3. Исходный снимок перед преобразованием сохраняется для сверки. События не переписываются;
   паспорт, правила, проектные связи, import-ID ledgers и операторские сведения сохраняются.
4. После миграции новые таблицы являются единственным источником текущих объектов и связей;
   прежний снимок служит архивным источником. Поддерживаемые старые ответы строятся как ограниченная
   проекция. Совместимые старые записи сайта меняют только прежние поля и документированные
   операторские ссылки; они не заменяют обнаруженные связи или всю новую коллекцию.
5. Добавить структурированные проверки и сопоставление. Не извлекать домен → приложение из
   сходства имён или свободных заметок. Не объявлять импортированные пути неиспользуемыми.
6. Ввести writer compatibility barrier в существующем механизме schema migration. Используется версия
   30 по актуальной схеме checkout. Рантайм, который способен стереть новые
   поля или связи, не допускается к записи.

Активация установленной версии и повторное обследование blue-ant — отдельные действия после
реализации. Откат после принятых записей опирается на проверенную резервную копию и согласованный
план сохранения новых данных; удаление таблиц ради запуска старого writer не является откатом.

## Проверка решения перед поставкой

Ключевые сценарии перечислены в [проектировании](../server-map-design.md#сценарии-приёмки).
Реализация дополнительно проверяет:

- точное сохранение старых идентификаторов, событий, паспорта, операторских правок и импортных ledgers;
- FK, CAS и атомарность публикации/отката при конфликте, включая конкуренцию с операторским редактором;
- повторы порций, неизвестный исход записи, устаревший отчёт и неполное обследование;
- поиск и порядок по полной коллекции, корректное продолжение после сокращения по байтам;
- бюджеты ASCII JSON, Unicode и negative disclosure на больших списках, сертификатах с множеством имён и ошибках;
- HTTP/SSE, ссылки и no-JS формы, сохранность черновиков, клавиатурный доступ и читаемость на узком экране;
- отдельную реальную проверку выбранного хоста после установки, без подмены её синтетическими тестами.

Кандидат реализован в checkout. Primary checks и отдельный синтетический Dashboard preview
сохраняются в run artifacts; независимая проверка и операторское рассмотрение обязательны
перед поставкой. Документ не утверждает установку обновления или аудит реального хоста.

Уточнение совместимой записи: квоты роста объектов и связей проверяются для всей транзакции
до первого переноса приложений и после всех добавлений ссылок. Запись сверх квоты не растёт
при правке других сведений; исходные мигрированные данные не обрезаются. После создания и
миграции старый writer переносит только новые явно добавленные элементы ссылочных списков.
Неизменённый старый список не восстанавливает операторское удаление объекта или связи.

При частичном наблюдении и правке формы прежние общие основания материализуются у уже известных
полей до замены общих дат. Отсутствие даты остаётся неизвестностью, а новый DNS или описание
не освежает прежнюю доступность, HTTPS, состояние службы или проверку продления. Все новые даты
карты, связи и этапов проверки проверяются на представимость в UTC до commit.

## Уточнение: понятная техническая картина (schema v31)

Операторское `usage` сохраняет решение человека о назначении, закрытии и хранении. Оно не
маскирует наблюдаемое состояние службы или HTTP. Чтение добавляет отдельный `understanding`
для выбранного объекта; компактные строки получают `observed_status`, `technical_usage`,
`observed_reason`, `effective_availability`, `entry_type_effective`, `effective_role`.
Те же вычисления используются Dashboard, фильтрами и сортировкой до пагинации. Состояние
`unknown` означает неизвестный общий результат; отдельные неизвестные поля остаются видимыми.

`technical_usage=current` требует свежую явную связь configuration/process с потребителем и
свежую датированную process/probe/configuration проверку запущенного/запланированного экземпляра
службы. Для приложения нужен связанный runtime; произвольная работающая зависимость не доказывает
запуск приложения. Даты связи используют inventory_hours, состояние службы — health_hours.
Импорт, reference, операторская ссылка без технической проверки и устаревшие результаты не дают
current. Ссылка конфигурации без подтверждённого текущего запуска даёт configured. Неполное
отсутствие не даёт candidate/leftover. Текущий потребитель запрещает новое решение leftover;
конфликт старого решения сохраняется и показывается как вопрос оператору, без изменения данных.
Положительная связь и публикация новых технических наблюдений не блокируются старым решением:
иначе реестр не мог бы сохранить обнаруженное противоречие. Явный upsert с leftover проверяет
новое/повторное решение; check_publish сохраняет прежние защищённые операторские поля.

Каталоги получают наблюдаемые `entry_type` и `consumer_checks` — перечень только полностью
проверенных источников docker/systemd/cron/proxy/symlinks для конкретного пути. Файлы, сокеты,
символические ссылки и неподтверждённые типы остаются записями, но явно отличаются от каталогов.
Прежняя датированная фраза контекста «Каталог.» может выбрать тип представления. «Файл или
отсутствующий путь.» остаётся неопределённым техническим путём; расширение имени не доказывает
тип. Никакая такая проекция не переписывает старые строки или решения. Неизмеренный размер и
неполный охват потребителей показываются отдельно.

HTTP-наблюдения получают `probe_scope=unknown|transport|endpoint|functional`, `probe_url`,
`expected_result`. Endpoint/functional требуют явный несекретный HTTP(S) URL и ожидаемый ответ.
Датированный транспортный HTTP403/404 с тем же основанием ответа не подтверждает поломку API:
выдача показывает unconfirmed, сохраняет исходный ответ и требует ожидаемый endpoint. Scope,
availability и public_result требуют совместимых probe-оснований, источников и дат; совпадение
времени разных источников не связывает их проверки. Для прежних
данных поддерживается только явная формулировка probe evidence «Корень API не является полной
проверкой приложения» с совпадающей датой public_result. Новый функциональный результат, DNS/TLS,
5xx и остальные ошибки сохраняют свои состояния. Наличие процесса не доказывает функциональный
успех. Более новая проверка без прежнего transport scope не наследует его вывод автоматически.
Прежние GET / маршруты и process-вывод приложения получают такое объяснение только по свежим
проверенным route/endpoint связям и совместимым полевым датам одной серии (не более минуты,
совпадающий source). Маршрут дополнительно требует тот же hostname и HTTP403/404, приложение —
явно подтверждённый runtime. Явные собственные HTTP5xx/curl/TLS/DNS ошибки из полевого основания
приложения не подавляются соседним root403/404. Связанная подтверждённая ошибка endpoint сохраняет общий error;
непроверенные связи не доказывают работоспособность. Общая checked_at не заменяет дату поля.
Свежий `origin_result` с собственным probe-основанием сохраняет внутреннюю HTTP/curl/TLS/DNS
ошибку до переинтерпретации root403/404. Публичная и внутренняя проверки могут иметь независимые
источники и даты; у каждой проверяются её полевые доказательства и health-интервал. Общая дата
при наличии доказательств других полей не подтверждает origin без его собственного evidence.
Связанное внутреннее предупреждение сохраняет общий error с именем точки, причиной, источником
и датой, отдельно от собственного публичного ответа маршрута. Это не доказывает использование
внутреннего TLS прокси или поломку функции API. Производное объяснение ограничивает длину
ответов/источников; точные наблюдения и полный provenance остаются в исходном объекте.
Dashboard явно разделяет изменившийся текущий вывод и сохранённую оценку доступности, приводя
источник/дату самой оценки. Рендеринг не меняет исходное availability, scope или историю.

Понятное описание связей не заменяет полную выдачу: до шести коротких ссылок на каждый тип с
полным total в understanding, все отношения по существующему links cursor.
Обзор related дополнительно ограничен 8 KiB ASCII JSON на все группы с явным omitted каждого
типа. Ограничение обзора не меняет объект, links_total или продвижение полного курсора. Domain48 KiB,
MCP52 KiB и request64 KiB сохраняются. Источники/команды не исполняются. Новые поля наблюдений
защищены writer barrier v31: миграция меняет только watermark, точные данные/история/ревизии
сохраняются; v30 runtime отказывает до чтения/записи. Отдельная установка и повторный аудит
реальных серверов необходимы для неизвестных ролей, размеров, полного охвата и ожидаемых URL.
